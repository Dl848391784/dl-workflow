## 0. 本节点与前例的结构差异（决定判面怎么切）

| 维度 | u:1#1-#5 / u:2#1 / u:2#2 | **u:2#3** |
|---|---|---|
| record_format | qa（#1-#4）/ statements（#5） | **qa** |
| mech_checks | varies（who/红队三件套/候选追溯/出处标注） | **无**（子3 无现有 mech；基线先判 judge 侧能否稳） |
| artifact 组成 | 单条 / 子1+子2 拼合 | **子1+子2+子3 三行拼合**——子2 aligned_goals 是子3 价值论证的对象（前序锚点），子1 是背景锚 |
| 命题性质 | 事实性（痛点）/ 结构完整性（对齐矩阵） | **规范论证**（受益者/价值链/量化基线/must-nice 提案）——基线可工具留痕，分层真值归用户（子5），judge 判「论证形式完整+非空泛非编造+提案语义」 |
| vio 类型 | 语义+形式混合 | **C1 空泛复述=语义 / C2 基线编造=形式（无留痕）+语义（真实性）/ C3 全must·分层无理由=语义 / C4 替用户拍板=语义**——语义主导，须按 #30 ⑫ 穷举违规形态 |
| gate 长度 | 291–2397 | **291**（最短档；#30「短 gate 也 thrash」第五实证候选） |
| 特殊判据陷阱 | — | **「nice 提案附理由」被误读成「nice=无 也必须单列理由」**（demo clean 有镀金理由仍被 block）——「必须/nice 逐项齐全」措辞歧义同 u:1#5 聚类 1 型 |

由此而来的设计约束：

1. **vio 类型判定（#30 ⑫）**：四条质量判据全语义主导。C2（基线编造）含形式子项
   （Bash 命令/输出/路径留痕在场与否=词形可判）+ 语义残余（留痕在场但数字真伪）。
   C1/C3/C4 是纯语义（空泛/无理由/拍板语义在场与否）——判据按类分治，语义类穷举
   违规形态为独立 block 条件，形式子项评估是否下沉 mech。
2. **「逐项齐全」措辞歧义**（同 u:1#5 #23 第二变体）：形式要件「+must/nice 提案附理由，
   逐项齐全」被弱 judge 解析成「每条目标+每条 nice 附理由都须单列」——demo clean
   的「nice提案=无。当前对齐目标集只有G1；额外提供因子名单…添加会形成镀金目标」
   （已附理由）仍被 block「nice 提案附理由未附说明」。修法=改表述（#23 修文本不站队）：
   钉死「每个目标的分层提案附理由；nice=无 时给出为何无 nice（镀金/未确认独立目标）
   即合规，不要求 nice=无 单独成条再列理由」。
3. **替用户拍板判据的判材在「提案-待用户裁决」语义**：demo clean 写「此为提案，未替
   用户拍板」；vio5 写「分层已定，无需用户再裁决」。合法形态=分层以提案口吻+显式
   留待子5 用户。钉死措辞须区分「提案附理由」（子3 合法）vs「拍板定案」（子3 违规，
   违规位在子5 用户裁决）。
4. **基线留痕的判材边界**：C2 判「无工具留痕出处=编造」。judge 看不到 Bash 会话原文，
   trace 内声明「Bash实测…」+ 命令/路径/输出=合法留痕形态；须钉「不得要求可复现性/
   更完整日志/补充 Bash transcript」（同 u:2#1 聚类 2 的「可核验性」发明要件族）。

### 1.1 误伤模式聚类（clean 6 轮判词逐字）

| # | 模式 | 判词摘录（逐字） | 性质 |
|---|---|---|---|
| 1 | **「nice=无 违反逐项齐全」**——「must/nice 提案附理由，逐项齐全」被解析成「nice=无 也须单列理由/自成形式」 | 「nice目标提案=无违反'nice目标提案是否存在'的逐项齐全形式」 | 判据文本自身措辞歧义（同 u:1#5 聚类 1 / #23 修文本不站队） |
| 2 | **受益者须「原话留痕/用户画像佐证」**——demo 已写「出处为用户自述原话'我自己'」，judge 仍要更完整佐证 | 「受益者'当前提问者本人'无用户画像或上下文佐证（仅称'自述原话"我自己"'但未提供原话留痕）」「受益者溯源不充分」 | judge 发明要件（判据只要求受益者，未要求原话转录格式） |
| 3 | **价值链痛点须「原话留痕/出处」**——痛点来自 ProblemContext，非本步重引，judge 补要 | 「未列明具体痛点出处（'没有缩减规则''候选太多'称引自用户原话但缺失原话留痕）」「痛点'候选太多'无 ProblemContext 原文出处支撑」 | judge 发明要件（价值链=目标→痛点→价值类型，痛点出处非形式要件） |
| 4 | **价值链须「拆中间环节/结构化展开」** | 「未拆出 value chain（如 baseline→target→outcome 的中间环节）」 | judge 发明要件（一句话价值链点名痛点即合规） |
| 5 | **基线须「可核验命令/输出/路径」**——demo 写「Bash实测最新default报告：…」，judge 要完整命令转录 | 「基线虽声称'Bash实测'，但未提供可核验的工具留痕出处（命令、输出或日志/文件定位），无法排除数字编造」 | judge 发明要件（「Bash实测…」+关键数字=合法留痕形态） |
| 6 | **must 理由误读为循环论证**——demo「若不能提供…本实例即未回答核心问题」是「不达成即失败」试金石，judge 读成「因为是核心问题所以 must」 | 「理由…本质是'因为是核心问题所以must'，未给出相对成本/风险的取舍依据」 | 循环论证判据误适用（合法 must 理由被当循环论证） |

6 类全从严 framing 下 judge 单向模式匹配过度 + 发明要件，与 u:1#1-#5 / u:2#1/#2 同根因。
误伤源=judge 发明要件为主（2/3/4/5/6 五类）+ 判据自身措辞歧义一类（1）——非纯词形可改
根除，预期需多轮迭代（非 ⑱ 一轮达标条件）。

### 1.2 载荷缺陷自审（#30 ⑦，先于 gate 迭代修）

vio3 双目标全 must 与 vio4 循环论证共享「无理由」判定面，两载荷文本上可区分——
vio3=有结论无取舍讨论（G1/G2 全 must、「都重要都必要」），vio4=理由循环（「重要所以 must」）。
vio1 基线「当前筛选效率不高」同时触发空泛（无数字）与编造（无留痕）两面，judge 判 block
理由重合属设计内，牙齿 6/6 维持。载荷集无修正项。

## 2. 设计决策

1. **framing 反转**：默认 pass + 明列 block 条件（「默认 pass」字面触发 run_judge
   双态同向指令行，v2.76 单源）。
2. **判据文本歧义修复**（聚类 1，#23 修文本不站队）：形式要件
   「+must/nice 提案附理由，逐项齐全」→「每个目标的分层提案（must/nice）附理由；
   nice=无 时写明为何无 nice（如镀金/未确认独立目标）即合规」。selfcheck 手写同词形
   同步改（#29：purpose 引用常量自动同向，selfcheck 是独立字面须手工）。
3. **方框判据（语义类穷举 + 形式类正面退路）**：
   - 一、空泛复述：无基线无痛点链接的「提升效率」式断言判 block；价值链以具体
     痛点+价值类型点名、或基线数字/不可量化标注在场即非空泛（短答案≠空泛，钉正例）。
   - 二、基线编造：数字无工具留痕出处（Bash 命令/输入路径/原始输出或「Bash实测
     +报告名+数据点」声明）判 block；「Bash实测…」式声明+关键数字=合法留痕形态，
     禁要求可复现性/补充 Bash transcript（聚类 4 钉死）。
   - 三、全 must 无真实取舍：多目标全 must 且无任何 nice 讨论/取舍理由判 block；
     单目标必须=must 且说明「不达成即失败」=合规，nice=无 附镀金理由=合规。
   - 四、分层无理由：无理由或「重要所以 must」循环论证判 block；理由=「不达成它
     本实例就失败/有 workaround 可继续」试金石=合规。
   - 五、替用户拍板：分层以定案口吻（「已定/确定为 must」「无需用户裁决」）无
     「提案-待用户裁决」语义判 block；「提案…未替用户拍板/最终裁决留给子5 用户」
     =合规形态。
4. **【关键】nice=无 的判据语义**：不得以「nice=无 未单列理由」block 已附镀金理由的
   trace（聚类 1）；不得以「缺 nice」block 单目标节点（demo 单目标场景=nice=无 合法）。
5. **【合法正例】**：demo clean 形态逐条对应误判类（nice=无 附镀金理由合规/价值链
   原话+价值类型合规/「Bash实测…」基线留痕合规/「此为提案，未替用户拍板」合规），
   方框以外一律不判。
6. **前序锚点**：子1/子2 trace 的存在与组成不作 block 依据（judge 只判子3 trace 的
   论证质量；子2 aligned_goals 是子3 论证的对象=锚，非判对象）。engine 注 v2.78/v2.79
   已全局覆盖，gate 内轻量提示即可。

### v1 关键现象与教训

1. **framing 反转即治 clean**（0/6→6/6，一轮）：6 类误伤全从严 framing 发明要件，
   反转+合法形态钉死后全灭——同 u:2#2 判断（主杠杆=framing 反转，误伤全是 framing 致病）。
2. **压跷跷板立现（v1）**：钉基线合法形态过宽——「Bash实测/命令/路径/报告名 声明=合法留痕」
   被 judge 宽读，「根据最近报告数据」也被当留痕放过，vio2 6/6→0/6（6 轮 pass 全空判词=
   默认放行下没查）。clean 的「Bash实测最新default报告」与 vio2 的「根据最近报告数据」
   仅差一个**工具动词**——词形可判子项（#30 ⑭），judge 侧不稳的经典 mech 下沉候选。
   **判别**：v2 先用文本穷举模糊声称形态（「根据报告数据/最近报告/数据显示/估计」）+
   钉工具动词在场，若 vio2 回炉线以上则免 mech（同 u:2#2 不走 mech 的路径）；仍 <5/6
   则按 u:2#1 范式下沉 `baseline_tool_trace` 生产墙（write 侧词形扫描零方差）。
3. **vio5 5/6=judge 注意力方差**（1 轮 pass 空判词），非判据问题；方框五 block 条件已被
   判词逐字引用（[1][2][3][4][6] 全部精准命中）。

### v2/v3 关键现象与教训

1. **v2（方框二 穷举模糊声称+钉工具动词）**：vio2 0/6→5/6 复原，但 clean 6/6→5/6、
   vio4 6/6→5/6 各掉一轮（clean 掉的是「nice=无 附镀金理由」误读——judge 把
   「添加会形成镀金目标」这一句就不算镀金理由；vio4 掉的是 pass 空判词=注意力方差）。
2. **v3（nice=无 镀金理由完整形态三处强化）**：clean 回 6/6、vio4 回 6/6，
   但 vio2 5/6→4/6（pass 空判词 [2][6]）——**方框二文本 v2/v3 完全相同，读数 5/6 vs 4/6
   纯 judge 注意力方差**。判据二「无工具动词=拍脑袋数字」是纯词形可判子项，
   弱 judge 默认放行下不查即过（空判词）——#30 ⑭ 触发位明确：**下沉 mech 零方差生产墙**。
3. **mech 设计 `baseline_tool_trace`**（u:2#1 answer_source_marker 同范式）：
   扫描基线题（q 含「基线/可量化」）答案——「不可量化」标注=合法替代跳过；
   无数字（`\d` 无命中）跳过交 judge（空泛复述兜底）；有数字但无工具动词
   （Bash实测/Bash命令/实测/python3/sqlite3/codegraph/运行/路径/输出/报告第/报告自身）
   =当场拒。离线三向验证：clean1「Bash实测最新default报告」过 / clean2 返工「Bash命令
   +python3+输出」过 / vio2「根据最近报告数据」拒 / 「不可量化+原因」过 / 无数字基线过。
4. **mech 下沉后 judge 侧变化**：方框二声明「基线留痕已机械校验——无工具动词的数字已被
   当场拒、不会到你这里」，判据二 block 条件删（judge 不再判基线留痕），或留薄语义残项
   （「留痕在场但数字与声明来源明显矛盾」）——本节点取**删**（judge 无法核验数字真伪，
   编造已由 write 侧 100% 拒，残项无可判真值，声明「不得以基线留痕为由 block」）。
5. **mech 生效约束**：子3 record_format=qa，`mech_checks` 在 append_trace qa 分支会执行
   （#17 判定可行，区别于 statements 归一化步）——下沉具备前提。落地时 `dl_flow_engine.py`
   加 `_check_baseline_tool_trace` + `_MECH_QA_CHECKS` 注册；`dl_flow_nodes.py` 子3
   mech_checks 加 `"baseline_tool_trace"`。
