# 编排节点拆步方法论（第一性原理推导链）

> workflow-creation skill 按需参考。设计新编排节点/拆 sub_steps 前必读。原 node-design.md §3.8 推导链部分迁此（节点结构索引在 nodes-index.md）；括注原编号供溯源。

## 1. 领域定位先于失效模式分析（原 §3.8 #0）

**领域定位先于失效模式分析**（2026-07-28 DesignSolution 初版被驳回 + understand:3 编程域修订，同一用户决议「编程专用工作流」两次兑现）：失效模式表是**领域相关**的——编程工作流的解必须锚定代码现实（「凭空设计」是不看代码就设计/引用不存在接口/重复造轮子，编程域主导失效族，通用域没有），消费契约倒推的产物形态也不同（理论方案 vs 代码级改动清单）。DesignSolution 初版套通用域失效模式表产出 5 步理论方案版，被用户「编程工作流不能只理论，要结合项目代码做代码设计方案」驳回——重做失效模式分析才多出接地族（5→6 步）。设计新节点前先问：**这个节点的命题在本领域（编程）里长什么形态**？

## 2. 终态三属性定目标（原 §3.8 #1）

**终态三属性定目标**：内容正确（中间步）/ 形式可移植（归一化陈述步）/ 用户认可（读回确认步）——三属性同构贯穿所有 understand 子阶段，末两步（归一化 + 带证据读回）是固定收尾对。

## 3. 命题性质三分定取证配置（原 §3.8 #2）

**命题性质三分定取证配置**（2026-07-27 从二分扩成三分）：
   - **事实性命题**（问题是否存在、约束是否真实）→ 需取证 + 质检裁决（judge 判结构、外部证据判真值）；
   - **规范性命题**（想要什么、范围取舍、must/nice）→ **无取证步**——外部证据无权证伪「我想要什么」，真值源只有用户（硬设取证步 = 逼模型拿「业界通常」式训练记忆冒充依据）；
   - **中间态（假设）**（未证明但当作真）→ 显式标注（置信度 × 错误时影响）+ **接受归用户**（风险承担是规范裁决，模型无权代答）。

## 4. 取证源深度定取证步数量（原 §3.8 #3）

**取证源深度定取证步数量**：五层外部源（OpenAlex/arXiv/SE/HN/GitHub）→ 取证过程与判断质量异族，拆双步（ProblemContext 子4+子5）；本地单层源（Bash/codegraph/Read 验证项目内部事实）→ 压缩为一步（ScopeAndConstraints 子2），独立质检步判无可判 = 纯烧 judge。 **档随原子走，不随步走**（2026-08-02 v2.40，designs/fetch-depth-tiering-design.md）：同一取证步内原子问题的深度可以异质（仓内可答/点查锚点/充分双向）——按步定档会把混合实例逼进最深档纯烧。模式三件套：**分类前置**（上游步定档+其 gate 判分类合理性——纠偏在便宜环节）、**执行步只执行不重判**（禁降档——弱模型不给二次裁量口）、**升档通道**（执行中发现不收敛可上报升级+留痕——质量兜底）。**默认档按失败模式不对称选居间**：漏取证=质量问题（难发现）、过度取证=成本问题（易发现）→ 拿不准归中间档。

## 5. 失效模式族定步数（原 §3.8 #4）

**失效模式族定步数**：先列失效模式表（每条带外部出处），再按族归并——异族拆开（judge 分步可判），同族合并（省 judge）。步数不是模板对称出来的（6≠5≠5≠5），是失效模式族数出来的。**设计期外部取证惯例**（2026-07-28 plan:2/plan:3 两例）：失效模式表的外部出处用 Tavily 检索（用户明示允许时），设计文档头部注明「设计期调研——与运行期 understand:1 子3『禁 tavily/WebSearch』约束无关」免误读；编程域失效模式优先找 LLM 工具使用/agent 失效的实证研究（tool hallucination 分类、tool overload 基准等），通用项目管理文献对编程域判据无效。

## 6. 每个新节点先写「关键不对称」（原 §3.8 #5）

**每个新节点先写「关键不对称」**：与前序节点的差异即设计轴心（ProblemContext=纯事实、GoalsAndValue=纯规范、ScopeAndConstraints=混合[约束事实+范围规范]、SuccessCriteria=混合[轴心=规范性目标的可检验化转换；**消费契约倒推**——产物字段从下游消费方（review:0 rubric 判定需求）倒推，不是拍的]、DesignSolution=混合[**创造性生成×代码接地双轴心**——首个创造性生成节点：对象不存在须发散（防 design fixation），解必须锚定本仓代码现实须勘察（防凭空 API/重复造轮子）；消费契约倒推同 SuccessCriteria，下游=plan:2/execute:0/review:0]、TaskBreakdown=混合[**保真转换×执行接地**——与 DesignSolution 镜像：输入对象已存在且已拍板，创造性已上游消费（**无发散步**，发散=逼编造伪候选），主敌换成转换失真（semantic drift，防=清点基线+追溯锚）与执行者视角虚构（零上下文 executor 消费编造锚点，防=锚点核验步）；消费契约倒推，下游=execute:0/executing-plans/review:0]、CapabilityToolSelection=混合[**有限枚举×配置接地**——能力空间=可枚举注册表非生成空间（无发散步），主敌是映射层失效：幽灵能力（ghost invocation，f̂∉F，防=注册表逐字出处）/能力错配（防=trigger 原文覆盖判据）/tool overload（防=最小集+显式不加载清单）/漏配强制项（防=强制路由逐任务核对）；消费契约倒推，下游=execute:0/using-superpowers/H15+执行映射/Agent 成本/overload 防线五方]、ExecutionPlanCheckpoints=混合[**时序控制×风险配平**——首个运行时控制结构设计节点（前七节点设计内容，本节点设计控制流：何时停/验什么/失败后去哪/谁可并行）+首个四源聚合节点；主敌是时序失效：检查点虚设（防=零判断词判据）/误差复利（防=阶段边界布点+goal anchoring）/密度失配（防=密度归用户裁决+可逆性×爆炸半径提案）/失败处置缺失（防=路由三选一预定义）/并行冲突（防=互斥面交集实算）/返回物无验收（防=返回契约）；消费契约倒推，下游=execute:0 orchestrator 愿景（executor 不自行分析+多 subagent 并行）/execute:0 rubric/understand:4 时机字段/review:0 证据/用户密度裁决五方]）——照抄前节点步数/结构而不重做失效模式分析 = 设计事故温床（各 design 文档「否决的替代方案」节都否过一个「全对称版」）。

## 7. 机制适配走查（内容设计之外的第二轴，2026-07-27 understand:4 沉淀）（原 §3.8 #6）

**机制适配走查（内容设计之外的第二轴，2026-07-27 understand:4 沉淀）**：#1-5 定的是「内容编排」（几步/每步干什么/判据），但新节点的**属性组合**（advance 类型 × hold × artifact × gate_mech）可能与机制函数的隐含假设冲突——understand:4 实例：hold 机制为 advance="sub" 设计（release_subgate 无条件 advance_state），直接套到首个 advance="phase" 的 hold 节点会把 phase 大闸门**静默吸收**（一次 /dl gate 穿两道门 + 产物 understand.md 失去写入窗口）；且编排节点 Stop hook 在子步骤门控分支即返回，PHASE_DONE 不可达。设计文档只写「需 pinning 测试」这种抽象预见不够——**设计期逐函数走查一遍**（读代码，不是读设计；机制断言——含讨论稿的「必须保留 X」式主张——先查最近同构先例的节点定义再下结论，2026-07-28 实例：讨论稿凭记忆主张 plan:2 gate_rubric 不能置 None，查 understand:4 先例[阶段出口编排节点 rubric=None + 机械门保留]后订正）：①末步推进（`_advance_sub_step` 对该 advance 类型的行为）；②门栏放行（`release_subgate` 推进否、推进后闸门语义）；③完成信号通道（STEP_DONE/PHASE_DONE 哪个对该节点可达）；④注入状态机（编排中/扣留/放行后每态模型看到什么）——**逐态文案也要走查**（2026-07-28 plan:2 沉淀）：「复用既有路径无新机制」只覆盖 engine 函数，注入**文案**可能藏着为先前节点硬编码的隐含假设（understand:4 第三态「汇总写产物（4 子阶段…）」=「放行后写产物」窗口假设，对产物在末步内装配的 plan:2 是错指令）——冒烟必须覆盖**三态**（编排中/扣留/放行后），不只编排中态；⑤/dl 命令路由（held 检测与 phase gate ## 8. 设计文档的修订留痕格式（原 §3.8 #7）

**设计文档的修订留痕格式**（2026-07-28 understand:3/4 编程域修订惯例）：已确认的设计文档做定位级修订时——头部加一行 `> 修订（日期，用户决议）：定位 + 改动点清单`，正文修改处嵌「（日期 修订）」标记——让后续读者分清原始设计与后补修订，且修订决议本身可溯源。

## 9. 数据面卸载是拆步的正交轴（原 §3.8 #8）

**数据面卸载是拆步的正交轴**（2026-08-01 v2.38 子3 子代理化）：#3 按取证源深度定步数，但**步内工具密度**是另一轴——外部取证类步骤的原始输出（curl/WebFetch 页面）是主会话上下文长度大头（成本=轮次×长度，§3.6 #8）。判据：步骤的产出是**蒸馏结论**而原料体积大 → 原料采集卸子代理（`*-prompt` 生成器 + 返回契约=蒸馏边界，§3.7 四件套），主会话只做 可检验化/派发/原文收录/内部层；产出是**判断/裁决**或原料本身小（codegraph/Read 仓内）→ 留主会话。编排结构（步数/gate/留痕要求）不变，只换执行位置——配套三件事：fence_allow 加 Agent（子代理进程工具经同一 PreToolUse 围栏，不区分主/子会话）、原文收录形式要件机械化（§3.5 #17）、红线规则随迁（§3.5 #18）。

## 10. 会话粒度是拆步的第三正交轴（原 §3.8 #9）

**会话粒度是拆步的第三正交轴**（2026-08-13 P2-4 段链合并，designs/segment-chain-resume-design.md）：#1-5 定门控粒度（步），#8 定数据面执行位置，**会话粒度**（一个会话覆盖几个步）是第三轴——三者独立可调。核心鉴别：**会话合并 ≠ 派发合并**——v3.0 §2.2 否「批量段」的两个理由（append-trace state 驱动错挂步号 / 弱模型多步指令跟随=一过率对立面）都只针对「一次派发多步」；「逐步派发 + `--resume` 同会话续跑」两个都不触及（步号归属由逐步派发保住，单步指令由每 prompt 只带当前步 purpose 保住）。**链边界三论证同指 minor_state**：①node-rules system prompt 按节点生成——跨节点续跑 system prompt 变 = 前缀缓存失效；②handoff_pack 交接（v2.45）在 minor_state 边界重置上下文——链不超边界则 v2 平方膨胀不复发（v2 教训边界 = 30+ 步无锯齿；链内 3-5 步峰值 ~150-250k 有界）；③交互步（TUI 段）/确认步（无会话）天然断链。续链不变式（链属当前节点 + last_step == cur-1）让 state-reset/back/jump/step-pass/TUI 全部**天然失配断链**，需显式断的只有 RC_INTERRUPTED（杀中段 transcript 尾或残半 turn）。**收益按 provider 缓存语义分流**：流式会话隔离 provider（deepseek 类）上 = 摊薄冷启动的唯一杠杆；流式全局共享 provider（kimi 类）上收益≈0——同一优化不同 provider 收益差一个量级，设计目标值必须按缓存探针矩阵（v4-cost 设计 §2.0b）分流写两套。

## 11. 取证源选择 = 先识别权威类型、定点抓，泛搜索兜底（原 §3.8 #10）

**取证源选择 = 先识别权威类型、定点抓，泛搜索兜底**（2026-08-13 amplitude_annualized sub3 审计）：「年化折算」是工程惯例不是学术问题——权威在业界标准库源码（empyrical/pyfolio），不在 OpenAlex/arXiv 关键词索引。light+full 两 agent 17 curl 仅 4 次有效（24%），其余泛搜索全空手/无关/权限受限；有效那 4 次全是「定点抓 empyrical 源码」。设计取证步（尤其方法论/量级合理性 claim）时三件事：①**先判权威类型**（学术论文 / 业界库源码 / 官方文档 / 定点网页——给模型一张 domain→权威源注册表，不靠它临场判断）；②**查询词翻译成业界术语**（禁 repo 内部黑话，如 coverage → annualization with missing trading days）；③**泛搜索（OpenAlex/arXiv/SE/HN）只作注册表无对应项时的兜底**。判据：claim 的权威是「单一已知源」还是「需泛搜索发现」——前者定点抓（高有效率），后者才泛搜。

## 12. 拆步重编号先查 sub_step_index 类型——int 就全重编号，别想后缀（原 §3.8 #11）

**拆步重编号先查 sub_step_index 类型——int 就全重编号，别想后缀**（2026-08-14 plan-first 拆步，understand:1 子2→子2a/子2b）：想给拆出的两步用 `2a/2b` 后缀标识，但 `sub_step_index` 全链路是 **int**（`sub_step_at(node, n: int)`、`range(1, sub_step_index+1)`、evidence 匹配 `sub_step == n`、`_iter_trace_segments(text, n)`、state 范围校验），加后缀要 int→str 改语义，波及 range/比较/evidence 匹配/state 一大片。int 约束下只能**全重编号顺延**（子2→2/3，子3-6→4-7），机制简单但波及面大——evidence 历史 sub_step 值全变 + 读回步挂载/segment chain 白名单/注入文案里的步号 + **跨节点"同构 ProblemContext 子N"引用**（别的节点 purpose 里指向本节点的步号）全要顺延核对。设计"拆一步成两步"前先 grep `sub_step_index` 消费面 + 跨节点步号引用，确认类型约束再定编号方案。
