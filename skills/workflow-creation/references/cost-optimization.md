# 提效与成本优化方法论（瓶颈分层/杠杆）

> workflow-creation skill 按需参考。优化耗时/token 消耗时读。原 node-design.md §3.8 提效杠杆部分迁此；括注原编号供溯源。

## 1. 提效优化先定位瓶颈层——搜索次数 / 判断思考 / 上下文膨胀是三个不同的层，在"搜索"层加工具碰不到"判断"层（原 §3.8 #12）

**提效优化先定位瓶颈层——搜索次数 / 判断思考 / 上下文膨胀是三个不同的层，在"搜索"层加工具碰不到"判断"层**（2026-08-14 amplitude_annualized step2 实测）：一整条线优化"搜索"（codebase toolbox 合一查询 / discovery ledger 去重 / `dl codebase trace` 全景 / 取证路线模板 / 围栏禁 grep），实测墙钟 6min 不降——因为瓶颈是**两次搜索之间的判断思考**（读工具结果 + 形成因果假设 + 决定下一步，最长 79s 间隔），不是搜索本身（单次 grep 0.3s）。最后 plan-first 拆步（把"规划思考"从"执行搜索"里分离成两步，即 #3 分类前置的兑现）才从 6min 降到 ~3min。教训：动手提效前先按 drive-stream 的 tool 间隔分诊——若大头是 **tool 间 gap（思考）** 而非 tool 数/单次耗时，那搜索工具优化（合一/去重/全景）全在错的层；判断思考层的杠杆是**拆步分离**（#3）或**上下文瘦身**，不是加搜索工具。实证判据：**tool 调用数降了但墙钟不降 = 瓶颈不在搜索层**（换个层，别在同一层继续堆）。

## 2. 框架通用 vs 项目专属边界——进框架的工具/模板只做代码结构语义，领域模板走 component B 注册（原 §3.8 #13）

**框架通用 vs 项目专属边界——进框架的工具/模板只做代码结构语义，领域模板走 component B 注册**（2026-08-14 codebase-toolbox 全程）：dl-workflow 会跑任意代码项目，任何进框架的工具/模板/方法论必须**跨项目通用**（codegraph/git/grep 的代码结构语义：symbol 定义/调用/影响面/历史），不能耦合任何项目的数据契约（回测 schema、report 数据流）。领域模板（如 factor 年化怎么拆）走 **component B 工具注册**（`<项目>/.claude/workflow-tools.yaml`）+ 项目级 skill，各自维护、不污染框架。设计进框架的东西先问一句「这是框架通用还是项目专属」——项目专属的硬编码进框架 = 换项目就废（"数据流"这种词就是项目语义，通用等价物是 codegraph 的 callees）。

## 3. 工具可用 ≠ 模型自动会用——新通道的「进入条件」要在该步 purpose/selfcheck 里显式声明（原 §3.8 #14）

**工具可用 ≠ 模型自动会用——新通道的「进入条件」要在该步 purpose/selfcheck 里显式声明**（2026-08-14 amplitude_annualized step3 修复后实测）：`dl codebase` 文案从 broken 的 `dl codebase` 改为可跑的 `bash dl-cmd.sh codebase ...` 后，模型确实用了，但探索面扩大 39%（+23 轮）。根因不是工具错，而是该步 purpose 只写了「取证路线」，没写「同类查询优先走 codebase、禁止为凑证据扩大探索面」的**停止条件**。给某个子步骤配新工具/新通道时，三件事一起改：①工具/文案（让命令可跑）；②purpose（明确何时用它）；③selfcheck（明确什么时候该停）。缺 ③ = 模型有枪没刹车。

## 4. 通路与台账要同时验收——`discoveries.jsonl` 生成是 `dl codebase` 被真实使用的硬指标（原 §3.8 #15）

**通路与台账要同时验收——`discoveries.jsonl` 生成是 `dl codebase` 被真实使用的硬指标**（2026-08-14 实测）：修复前模型用 raw grep/裸 codegraph，工作流目录无 discoveries.jsonl；修复后 `bash dl-cmd.sh codebase ...` 可跑，ledger 首次生成 18KB。检查台账是否生成，比检查「模型有没有被 deny」更能证明工具通道真的生效。

## 5. 文案约束管不住弱模型的步骤越界——「只做 X」要用机制堵入口，不是靠 purpose 劝阻（原 §3.8 #16）

**文案约束管不住弱模型的步骤越界——「只做 X」要用机制堵入口，不是靠 purpose 劝阻**（2026-08-17 amplitude_annualized 6 轮对照，v2.44 探索预算）：子2a purpose 明文「只规划不挖链」，弱模型 deepseek-v4-flash 仍跑 38 次 codebase/find 探索、56 轮、上下文胀到 114k（子2b --resume 继承后 fresh 124k）——它把执行冲动（定位实现符号）提前到了规划步。**文案约束对弱模型结构性失效**：它读得懂「只规划」但控制不住「想先查清楚再规划」。机制解 = `Step.max_explore_calls` 探索预算：drive_mode 段工人对 codebase/find/codegraph 探索命令机械计数，超限 PreToolUse 硬 deny（堵入口，deny 文案指路回本步交付物 atomic_questions）。iter5/6 连续验证：子2a 稳定 15-17 轮、6-7 次探索（预算内收敛，零 deny）、合计耗时 692s→365s（-47%）、成本 -50%。**判别准则：一个「只做 X 不做 Y」的步骤边界，若 Y 是弱模型的自然冲动（先查清楚再动手），文案约束必失效，唯一可靠的是 PreToolUse 计数/白名单类机械拦截。** 与 #12（瓶颈分层）互补：#12 定位「思考层」后，本条给「思考层失控」的机制解。

## 6. 零和游戏检测——把活从步骤 B 搬到步骤 A 不叫优化，叫转移（原 §3.8 #17）

**零和游戏检测——把活从步骤 B 搬到步骤 A 不叫优化，叫转移**（2026-08-17 u1-sub2b-consumes-sub2a 实测翻车）：让子2a 手写 `symbols`/`files` 字段「为子2b 锁定取证入口」，实测子2a 16→119 轮爆炸（$1.52→$14.55），子2b 只 35→19 轮——**净亏 2.3×**。教训：优化前先问「这个动作总工时变了吗，还是只是换了步骤受罪」。真正的优化是**消灭**动作（子2b 不再重新探索），不是**转移**动作（把探索推给子2a 手写）。检测信号：上游步骤轮数暴涨而下游只省一点 = 零和；下游省的 > 上游涨的 = 真优化。配套：**让模型手写它需要「凭空想」的产物（符号清单）= 把最难推理活塞给最弱环节**；机械能从已有行为导出的（工具落账），就别让模型手写。

## 7. grep 命中面 ≠ 取证起点——字符串搜索的命中文件清单是噪音不是信号（原 §3.8 #18）

**grep 命中面 ≠ 取证起点——字符串搜索的命中文件清单是噪音不是信号**（2026-08-17 string-files 注入翻车）：把 `dl codebase query --string "annual"` 命中的文件自动落账并注入子2b 当「取证起点」，结果 350 个文件（test_cases/docs/MODULE.md 全命中）灌进 node-rules，注入块 18.8K chars 反而膨胀上下文。**字符串搜索是「面」（命中一切含该词的文件），结构查询（trace/callers/history）才是「点」（file:line 精确锚点）**。取证起点只能来自结构查询，不能来自 grep 命中面。判别：注入给模型的「起点清单」若含 test_cases/docs/规范文档 = 噪音混入，真正的代码锚点不会被这些词命中到前几名。

## 8. step2→3 这类「--resume 续链」的上下文膨胀，根因是前一步轮数失控，不是注入大小（原 §3.8 #19）

**step2→3 这类「--resume 续链」的上下文膨胀，根因是前一步轮数失控，不是注入大小**（2026-08-17 fresh 124k 误诊纠正）：实测 step3 首调 fresh 124k，先以为「deepseek 流式会话隔离缓存」或「注入膨胀」，实际查 drive-stream token 流向——step2 跑 52 轮会话内上下文累积到 114k，step3 `--resume` **继承**这个 114k。**同会话续链时，fresh 大头 = 前一步的 transcript 长度**，注入（node-rules 9.7k + 交接包 9k + PROJECT.md 23k）只占小头。诊断 fresh 膨胀先分两种情形：①跨段新会话（真 cold start，provider 缓存语义相关）②同会话 --resume（继承前一步 transcript，前一步轮数是主因）。情形②的杠杆 = 压住前一步轮数（#16 探索预算），不是注入瘦身。

## 9. 缓存经济性 ≠ 机制语义正确——前缀缓存类机制的验收 = 逐段首调 cache hit 率实测，provider 间不可外推

**缓存经济性 ≠ 机制语义正确**（2026-08-17 u1-sub4-cost，u:1 段链回滚）：P2-4 段链设计期在 kimi 端点冒烟「--resume 跨进程记得内容」通过 = 只证**语义连续**，成本模型却假设「同会话续轮前缀全热」——deepseek-v4-flash 实测**时灵时不灵**（D 轮链内 step2→5 首调 fresh 44k→109k→166k→241k、hit 0.9-4% 全冷；F 轮 step4 hit 158k 暖）。冷轮时链 = 纯增税（每步首调重付单调涨的继承上下文），暖轮也比 fresh 段贵 ~2 倍（每轮重读 ~160k vs ~70k）。**验收口径**：缓存类机制上线后逐段查**首调 `cache_read/(input+cache_read)` 命中比**——<5% = 缓存没生效，与机制语义对错无关；provider 间缓存语义不同（全局共享/会话隔离/连接级），一端实测结论不可外推另一端。**§8 情形②的第三杠杆**：压前一步轮数之外，护栏突破/缓存经济性证伪时杠杆 = 断链本身（fresh 段首调 ~45k 恒定，不随前序轮数涨）。**配套范式**：扩面类裁决把回滚条件写成机械阈值（链峰值 250k）做预授权——突破即执行回滚无需再裁决（本次 D 轮峰值 324k 突破即据此回滚 u:1；u:2/3/4/plan 族峰值未破保留，surgical）。

## 10. 子代理等待的机制解 = 派发前移（预派发 overlap），完成信号按进程语义设计

**子代理等待的机制解 = 派发前移（预派发 overlap），完成信号按进程语义设计**（2026-08-17 u1-sub5-cost，designs/u1-sub5-cost-optimization-design.md）：step5 红队跑 158-235s 是墙钟地板，purpose 早钉「先派发后内查」（v2.39）但弱模型遵从不稳（轮2 派发 26s 后即 block 干等 2.7min 零并行）——文案无解的等待，机制解 = 输入冻结点一满足就由 **driver 预派发**（子4 gate 过后证据即冻结），worker 与下一步段并行，收录侧引擎子命令阻塞等完工。**完成信号三坑（全部实测逮住）**：①**僵尸**——父进程（driver）存活期间 worker 完工成僵尸，`kill(pid,0)` 仍成功会把阻塞等待拖到超时，须读 `/proc/<pid>/stat` state 判 Z；②**stdout 污染**——`ANTHROPIC_LOG`/包装器调试输出混入 stdout（冒烟 report 11.9KB 大头是 `[log_*]` 请求转储），spawn 实用型 claude 一律 `--output-format json` + 末行 result JSON 提取（judge 同款，is_error 按无产出）；③**新鲜度按内容不按时间**——state-reset 后前序证据变 → prompt sha1 变自动杀旧重派，sha 同 +（pid 活 | 报告在）= 复用。**配套**：预派发时代模型的「未收录提前提交」洞要补 mech 闭环（worker.json 在位=已派信号，gate 文案被告知形式要件已机械拦截就不能留无信号空档）；预派发声明走 Step 字段（pre_dispatch）单源，禁 driver 硬编码步号。

## 11. 词形判据的候选集先锚「真实词形长什么样」——float repr 与 hex id 撞车

**词形判据的候选集先锚「真实词形长什么样」**（2026-08-17 u1-sub5-cost 修1）：`_TASK_ID_RE = \b[0-9a-f]{16,17}\b` 与证据里的 Python float repr 小数位撞车（0.49519773767901265 → 17 位纯数字串），3 轮实测 4 次假阳性「已派发未收录」拒，模型为过关被迫改写合法证据数值。与 step4 防重误报（task_id 子串匹配撞派发留痕）同族：**词形类机械判据设计时，先拿「判据扫描的内容域里长得像目标的东西」做负例集**——task-id 的内容域 = 证据文本（float/覆盖率/时间戳密布），hex 词形必须加「含 a-f 字母 + 前邻非 hex/`.`（排小数段与科学计数法 e 段）」；放行方向留 judge 兜底（纯数字真 id 概率 ~(10/16)^17，漏识别=宁纵勿枉），误报方向不可接受（每轮 1-1.5min + 4-6 次全上下文调用的返工税）。测试双侧：误报 id 逐字入 fixture（不命中）+ 真 id（命中）+ v2.118 原牙齿（真缺席仍 BLOCK）。

## 12. 预派发（子代理与主会话并行）成立两判据：输入冻结点 + prompt 100% 脚本可生成——缺一就是质量陷阱

**预派发成立两判据：输入冻结点 + prompt 100% 脚本可生成**（2026-08-17 u1-sub5-cost 红队预派发落地 + u1-sub4 round-2 fetch 反例对照）：红队预派发成立因为①输入在子4 gate 通过即冻结（证据=子1-4 最新 trace，不含子5 结论=redteam-prompt 模板机械保证）②prompt 全由脚本生成（证据+纪律+输出格式，模型零补充）。fetch agent 预派发**不成立**：claim 可检验化（claim-A1「证实标准：权威库源码出现 X；证伪标准：Y」）是模型真语义工作、决定证据针对性（三关质检第一关），脚本预生成=降级取证质量；且预派发只省 setup ~1.4min（agent 运行 4-8min 才是大头）——质量风险 >> 墙钟收益。**判据形式化**：预派发省的是「setup 时间」，不是「子代理运行时间」——运行时间占大头时预派发收益天然小，先看 prompt 能否 100% 脚本生成，再看 setup 占比。**配套观察**：`claude -p --tools Read` 的工具限制**只限内置工具，不覆盖 MCP 工具**（红队 worker 经 MCP 调了 1 次 tavily_extract——未违规但超出「Read 为主」字面；要封 MCP 得靠 settings/权限层，不能靠 --tools）。

## 13. provider A/B 必须 token/墙钟双轴验收——缓存红利 ≠ 墙钟红利；前缀削减要用逐调用口径读数

**provider A/B 必须 token/墙钟双轴验收**（2026-08-17 u1-overall-cost 三方实测，designs/u1-overall-cost-optimization-design.md §5）：kimi k3（流式全局缓存）同问题整轮 fresh -42%/cache_read -30%/out -57%（首调 fresh 17.8-21k vs deepseek 37-60k，全局缓存命中 ~50% 前缀），**但墙钟 2.1×**（k3[1m] high-effort 段内均 31s/call vs deepseek 14.5s/call，且随上下文涨到 70s/call）——缓存红利只省 token 不省时间，单看 token 会误判「全面更优」。**配套口径**：固定前缀削减（禁 MCP schema 2.5k/调用 + node-rules 瘦渲染 25k→1.2k 字符 ≈ 9k/调用）这类**逐调用固定量**优化，总账读数会被步骤轮数方差（同步子3 30→70 calls = ±5M cr 摆幅，#22 同族）淹没——验收用**逐调用口径**（首调 fresh / cr÷calls），不用全轮总账；总账只在多轮连续下同口径比较（#40）。**MCP 纪律补丁**：`--tools` 白名单只限内置工具、限不住 MCP（红队 worker 经 MCP 调 tavily_extract 实证）——禁 MCP 要 `--strict-mcp-config --mcp-config '{"mcpServers":{}}'` 结构封死（engine.NO_MCP_ARGS 单源，段会话/TUI 段/预派发/judge 四处 spawn 统一挂）。

## 14. 材料随迁——下游会话所需材料的交付点选在「上下文里已有该材料的会话」；识别信号 = 串行两会话各全量读同一文件

**材料随迁**（2026-08-18 u2-sub1-cost，designs/u2-sub1-cost-optimization-design.md）：u:2#1 的 prep 段与 Q&A 会话**各读一遍 63KB evidence 全量**（各 ~21k fresh，Q&A call2 +16.7k fresh 实锤）——prep 读它设计问题，Q&A 读它找写 trace 的出处，而 Q&A 需要的材料（子1 用户原话）在 u:1#6 段会话的交接包里**本就在场**（本节点前序 trace 全文通道）。解法：材料的交付点选在「上下文里已有该材料的会话」——由它**逐字收录进交付载荷**（need_user.json 加 sources 字段），下游会话钉「直接引用、已覆盖处禁重读全量（未覆盖才按指针补）」，实测下游零 Read evidence。**识别信号**：审计段会话工具序列时，两个串行会话 Read 同一个大文件 = 重复付税，第二份的读取就是可消灭项。**与 #6（零和游戏）的判别**：这不是转移——上游收录的边际成本 ≈ 输出几 k（材料已在上下文、零读取），下游省 = 全量读 fresh + 后续每轮 cache 背着该文件；上游涨的 << 下游省的才动手。与 #8（数据面卸载）同族不同向：#8 把原始输出卸出主会话给子代理，本条把材料随交付物带给下游会话。**设计问句**：给下游会话配输入材料时问「哪个已存在的会话上下文里已有这份材料」——交付点就设在那，别让下游重新读文件。

## 15. 「下一个 X」类 lookahead 按「下一个有模型会话的步」定义——无会话步横在中间会让同节点 cur+1 式查找结构性失效

**lookahead 语义 = 下一个有模型会话的步**（2026-08-18 u2-sub1-cost 修A）：NEXT_PREP（工作段顺带备下一交互步问题清单）原 lookahead 只看「同节点 cur+1」——u:1#6 的下一步 u:1#7 是 confirm 级读回（P3-1 后**无模型会话**），于是 u:2#1 落回独立 prep 段（57-128s/47-65k fresh 纯系统税），confirm 步横在中间是 prep 段存在的唯一原因。**扫描三态**（泛化到任何「找下一个 X 步」场景）：①无会话步（confirm/机械步）跳过——它无问答无交付可顺带；②撞有会话工作步即停返回 None——**不抢**：该步自己的段是更好的顺带交付点（它运行时上下文更新更全）；③命中目标类型才返回。**跨节点配套**：prompt 必须**指名目标步全 id**（「为下一交互步（understand:2#1）备问题清单」）——不指名时模型默认「同节点下一步」，跨节点顺带交付会被误解/漏做；stash key 同样按目标步全 id 写（消费侧本就以被消费步自身 id 查，天然对齐）。**判别问句**：写「下一步/下一个 X」类查找时问「中间隔着无会话步时这个查找还命中吗」——「下一步」的语义要按编排的**会话边界**定义，不是按 state 指针 +1。

## 16. 「材料已在包内」步的通用「按需 Read」指针 = 反指邀请——声明式置位 + 条款 + 指针条件化三件套，置位前置是逐字段核对

**pack_self_contained 三件套**（2026-08-18 u2-sub2-cost，designs/u2-sub2-cost-optimization-design.md）：#14（材料随迁）的平移变体——材料**本就在交接包内**时无需随迁，但弱模型仍保险性全量重读：u:2#2（非交互推理步）的矩阵输入（子1 trace 全文 + 前序节点 statements 全文）100% 在包内，模型仍 ls/wc 侦察后 Read 68KB evidence 全量（+19.6k fresh/+43s，trace 内容核对零信息增量）——动机 = 包尾通用「以上为摘要；按需 Read evidence」的邀请 + 段 prompt 无材料边界条款。三件套：①Step 声明式字段 `pack_self_contained`（单源，禁硬编码步号）；②段 prompt 铁律加「材料边界」条款（直接引用，禁全量翻找，缺口按指针定点补）；③包尾指针条件化（置位步改「材料已在包内」——通用邀请与条款直接矛盾，两个强信号打架弱模型必违规，症状 F 族）。**置位前置 = 逐字段核对「本步输入契约 ⊆ 包内内容」**，并加装配不变量测试（包须含 X/Y 全文）——防未来 P1-1 类包修剪把材料修没了条款变错；未核对禁置位。实测：#2 段 fresh -34%/cr -53%/墙钟 -66%，零 block。**判别问句**：审计段会话工具序列时，非交互推理步冷启动后第一个动作是侦察+读大文件 = 先问「它要的东西是不是已经在 prompt 里了」。

## 17. 段链会话的一次大读取成本 = 本段 fresh + 驻留 × 后续每段冷启动——审计段链要把下游段数乘进读取成本

**驻留污染链式下游**（2026-08-18 u2-sub2-cost 实测）：deepseek 类端点段链（同 session --resume 续跑）每段首调必冷全量重写（[[deepseek-stream-cache-session-scoped]]）——段内一次 68KB 读取不止付本段的 +19.6k fresh，它**驻留会话上下文**，后续每段冷启动各重付一遍（基线 u:2#2/#3/#4 冷启动 39k/80k/103k 单调涨，delta 主体就是 #2 那次读取的残留；灭读后 #3 冷启动 -25%）。**审计口径**：段链会话里一次大文件读取的真实成本 = 本段 fresh +（文件体量 × 后续段数），乘以段数后再排优化优先级——单看本段会低估 2-3 倍。**与 #14 的合流**：材料随迁/禁读条款的收益同样要按「本段 + 下游各段冷启动」合计报价（本轮 u:2#2 合计 -29%，单段只 -34% 中的部分）。

## 18. 种子 A/B 的数据漂移混淆——种子 evidence 与现状数据真实漂移会驱动被测步的合法探索增量，对比口径须剔出混淆步

**种子 A/B 漂移混淆**（2026-08-18 u2-sub2-cost 实测）：种子 evidence（数天前的真实 trace）起跑做 A/B 时，若被测链路含「实测现状」类步（Bash 基线测量），种子快照与现状数据的真实漂移（本轮 default json annual 0.495→0.1277、ob_quality 0.492）会驱动该步合法的跨文件核查探索（+10 调/+82k fresh）——这是数据漂移驱动的真实工作，**不是优化失效也不是优化效果**，同口径不可比。对比口径：把混淆步剔出作用面，只比无混淆面（本轮 = #2 段本身 + #3 冷启动缩量，足额达标）；设计文档里显式声明混淆项与剔除理由，全轮总账更不直比（#22 纪律的漂移变体）。**判别问句**：A/B 某步数字反向大涨时先问「两轮之间这步的输入数据变了吗」——变了就是混淆项，剔出而非解释。

## 19. 「材料完备性核对」操作化——引用跨度逐字匹配 + 事实项双向核对 + 利用率分解 + 新综合占比；搬运型步才是 pack_self_contained 候选

**四步核对法**（2026-08-18 u2-sub2-cost 复盘，回答「前序材料有没有帮助/帮助了多少」时落成可复制操作）：#16 的「置位前置=逐字段核对」若无操作方法=主观拍脑袋，本条目是牙齿。对目标步的真实 trace 做：①**引用跨度核对**——提取 trace 里「…」引文（≥8 字），逐条查是否逐字出现在前序材料（带省略号截断的引用会字符串匹配失败，人工确认内容同源即可，u2_sub2_ab 实测 5/5）；②**事实项双向核对**——列目标步产出的关键事实清单（标签/数字/指针/类目），逐项查「trace 含 ∧ 前序材料含」（实测 8/8）；③**利用率分解**——按包内分节算哪节被消费哪节是死重（实测：PC 子6 陈述全文全用、GAV 子1 主体全用、**PC 子7 确认级读回记录 0 利用=死重**——确认级读回是机械通过记录无内容价值，P1-1 类瘦身候选；注意 decision 级读回含用户裁决不能一刀切）；④**新综合占比**——trace 里非搬运部分（推理/判断/关系标注）占多少。**判别规则**：事实 100% 可溯源 + 材料高利用 + 新综合是「基于材料的判断」而非「新事实产出」= 搬运型步 = pack_self_contained 合格候选；新综合占比高（产出新事实）或材料利用率低（大量包外取证）= 不该置位。**反过来说**：做完 A/B 后用同一套四步复盘，能回答「前置断言是否闭环成立」（本次：优化后模型零外部读取完成交付，且引用 5/5、事实 8/8 均可在包内找到=置位前提实测定案）。

## 20. 段链保留/断链判据 = provider 缓存语义 × 冷启动口径——「峰值未破保留」是防爆默认非成本最优

**段链成本重审**（2026-08-18 u2-sub3-cost，designs/u2-sub3-cost-optimization-design.md）：SEGMENT_CHAIN_NODES 的「峰值 <250k 保留」决议是防爆默认（没破就不动），不等于成本最优——成本优化立项时要按 **provider 缓存语义**重审每个链节点：会话隔离缓存 provider（deepseek 流式，P0 实证）上链**恒冷**（u2_sub1_ab/u2_sub2_ab 两轮 #3/#4 段首调 cache_read=0 实锤），链 = 每段首调全量重写单调涨的继承 transcript = 纯增税（#3 冷启动 60.3k=本步 fresh 73%、#4 94.1k=98%）；fresh 段首调恒定 ~40-45k（harness+node-rules+交接包+step prompt）不随前序轮数涨。**断链机制=白名单摘除，零新机制**（白名单即回滚面，fresh 段是 pre-P2-4 已验证行为；前置=交接包材料完备性逐字段核对 + 残留链下次查名单自然失配无需迁移）。**验收口径 = 段首调冷启动 fresh**——链税的直接度量，与步体方差（#40）天然分离；设计文档预登记「本体只比冷启动」混淆声明，否则步体轮数方差（同一步三轮 11/18/25 调）会淹没归因。实测：#3 冷启动 -33%/#4 -53%/链税面合计 -45%，#4 fresh 总计 -43%墙钟 -45%，零 block。**审计口径增量**：段链节点的成本大头在**各段首调之和**（首调主导，#4 冷启动占段 fresh 98%），不在段内调用——审计段链节点先拆「首调 vs 段内」两桶，首调桶的杠杆是断链（本条），段内桶的杠杆才是探索预算（#16 原 §3.8 #16）/材料边界（#16 pack_self_contained）。**判别问句**：段链节点成本审计先问「这个 provider 的链首调 cr 是 0 吗」——是 0 则链是纯税，断链优先于一切段内优化。

## 21. 段边界税的根治 = 段内续步（同进程多轮 stream-json）——断链只是把税压到恒定地板，续步才消灭地板

**段内续步**（2026-08-18 u2-sub4-cost，designs/u2-sub4-cost-optimization-design.md）：#20 断链后每步仍各付一次 fresh 段恒定地板（~40-45k = harness+node-rules+交接包+step prompt），交接包瘦身天花板 ~5%——**「每步一个 claude 进程」本身才是税**。根治 = 白名单节点（engine.MERGED_RUN_NODES）连续非交互步在同一 `claude -p --input-format stream-json` 进程内续跑：driver 保持 stdin 常开，每步 gate 过后把下一步任务 prompt（**剥交接包的续步变体**——会话内已有真迹）作为新用户消息注入。**与段链的本质区别**：段链 = 跨进程 --resume（deepseek 会话隔离缓存下恒冷、继承 transcript 单调涨重写 = 纯增税）；段内续步 = 进程内多轮（暖缓存成立——探针 turn2 fresh=95/cr 暖/1.4s vs 冷启 8.3s）。gate 逐 turn 照跑（牙齿零变更），block = 会话内暖返工（不再重付冷启动），escalate/none 上限/NEED_USER/中断/进程死全部收段回主循环按既有语义处置（state 在磁盘 = 优雅降级）。ctx 破 250k（链峰值同阈值）收段防驻留膨胀。**前置验证 = 生产旗标组合探针**（--session-id × --settings × --append-system-prompt-file × stream-json 输入，凭证从 bashrc 函数体运行时不进命令文本；探针纪律 cwd=/tmp 无 workflow settings）。实测（u2_sub4_ab）：#4 首调 fresh 44.6k→3.5k（-92%）、#4 fresh 总计 -77%、墙钟 -43%、零 block、trace 质量不降；**cr 预登记 +30~50% 实测仅 +3.5%**——续步轮顺带灭了 scaffold 返工褶皱（调用数 10→6）抵消单次 cr 增长，#3+#4 合计 cr 反降 6.5%——预估 cr 涨幅时别忘了续步消灭的返工轮也是 cr 减项。**判别问句**：某步冷启动占本步 fresh >50% 且步体是搬运型小活（overhead:work >10:1）= 段内续步候选；步体本身重取证高方差（u:2#3 测量型 11-31 调）则先审步体（#16/#19）。

## 24. 续步 vs 断链的抉择口径 = 首调税 vs transcript 携带税 + 暖率彩票；A/B 驱动轮代码路径核验不可省

**A/B 驱动轮代码路径核验不可省**（同轮踩坑）：bashrc `dl()` 体内写死 `$DL_WF_HOME/scripts/workflow/dl-launch.sh`（主树），**AC_WORKFLOW_LAUNCHER 只有 ac-* provider 函数的 --dl 路径读取**——用 `dl <name>` 跑 worktree 代码验证 = 静默跑主树（本设计 ab/ab2/ab3 三轮误跑链，把段尾暖调用误读为「续步边界暖」后才发觉）。三纪律：①验证 worktree 代码必**直调 worktree launcher**（`bash <wt>/scripts/workflow/dl-launch.sh --workflow <name> --headless`）；②跑完先核 driver 日志特征行（「⟂ 段链续跑」vs「段内续步」）确认代码路径再读数；③**turn 边界归属按段 fresh 总数逐调用配平**（段尾调用 vs 下段首调的分界，配平式 51,561+3,818+257=55,636 精确命中才定界）——误配平会把段内暖调用当成续步暖边界，整个 EV 结论反转。**种子实例组装五件套（裁 evidence 到目标步前一条/裁 last_judged_trace/清段记录/settings 验 name-agnostic/handoff_pack 起跑前冒烟）单源 = runtime-audit #25，本条不复制。**

## 25. 复用类条款必须写成「默认零新查询+逐项例外」——「缺口才新跑」宽松 license 会被弱模型读成主动找缺口验证（预算再投资形态）

**复用条款的写法决定步体方差**（2026-08-19 u3-sub3-cost 四轮 A/B，designs/u3-sub3-cost-optimization-design.md §6）：u:3#3 基线 13 工具调用中 9 个是子2 已覆盖事实的重复取证（同符号 impact/同文件 grep/同 file:line 重读），但 purpose 修订成「改动面取证**优先复用**子2 留痕，**仅缺口**才新跑」后，三轮实测模型把省下的预算**再投资**于更深的合法取证（发现 daily companion 文件纠正子2 C4 假设=质量真实收益，但 cr +87%/墙钟不降）——「缺口」是开放谓词，弱模型会主动制造/搜索缺口来合法化新查询（roam 工具还会从 codegraph 切到 grep 规避条款字面）。**收紧形态**才达标：「子2 已查过的符号/文件**本步零重查**——引用子2 是默认形态，新查询=逐项例外（in 侧条目缺实现指针且子2 无出处时单点补一次）」，第四轮工具调用 13→4（scaffold/Read/Edit/落库）、段 fresh -64%/cr -67%/墙钟 -46%、trace 指针 100% 可溯源子2 留痕零编造。判别问句：写「优先复用 X，仅 Y 才新查」类条款时问「Y 是开放谓词还是枚举例外」——开放谓词（缺口/未覆盖/必要时）= 邀请探索，枚举例外（缺指针的条目、逐条单点）才可收敛。**配套**：取舍要明示——默认零新查询=放弃消费步对前序「已验证」事实的独立复核（本轮放弃的日序列纠偏归子2 职责+plan:2#3/execute 还有后续防线），别把消费步写成半个验证步。**#16 泛化第二例 + #23 粒度下沉**：pack_self_contained 置位 u:3#3（消费型步判别=下游 trace 全文在场+ab 轮零 evidence 读取实证；第二轮包尾通用邀请诱发 15 次 evidence/state 元探查，置位后归零）；Step 级 `segment_strip_project_context` 首例（Node 级 B1 决议不下放到消费型子步——同节点内生成/验证步要规则原文在场，消费步的规则内容经前序 trace 逐字在场可单剥，首调 -45% 四轮稳定 14,341-14,406）。

## 26. 格式猎捕——模型为规避机械拒绝去引擎/测试源码反推校验实现，条款钉死「格式真源=scaffold 骨架+报错文案」

**机械校验的披露会诱发反向工程**（2026-08-19 u3-sub4-cost，designs/u3-sub4-cost-optimization-design.md §1/§6）：u:3#4 基线 22 工具调用中 9 次在 grep/Read ~/.dl-workflow 测试源码（【statements】/【text】/boundary/_ID_RE/_parse_trace_md）——purpose 披露「编号传导机械核对缺传即拒」却不说明「核对细节毋需预知」，弱模型为一次写对去反推校验实现（跨仓 roam，比 evidence 元探查更贵）。修法=purpose/selfcheck 通用条款：「载荷格式与编号传导的唯一真源 = --scaffold 骨架 + append-trace 报错文案（四桶分工：格式归脚本）——禁读引擎/测试源码反推校验实现；被拒按报错文案逐字修即可」。**哲学**：「写对」的责任在骨架与报错文案的表达力，不在模型预知校验细节——披露机械校验的目的是让模型知道「有这么个检查」（防 Goodhart 分层不破），不是邀请它研究检查本身。配套同轮：u:3#4 置位 Step 级 strip（第二例）+pack_self_contained（#16 第三例），一轮 A/B 全达标——首调 -38.4%（与探针 -11.9k 精确一致）、段 cr -86.3%、成本等效 -68.5%、墙钟 -46.3%、工具序列 22→5 理想最小形态（Skill→scaffold→Read 骨架→Edit→落库）。判别问句：消费型步的工具序列若超出「Skill/推理 → scaffold → Read 骨架 → Edit → append-trace」骨架五件，逐条问「这个调用在产出交付物还是在为条款找合法化依据/反推校验实现」——后者=文案漏洞不是模型问题。

## 30. 免跑基线提取法 + 段墙钟=输出量主导（dur_api≈out/rate）——token 优化的墙钟口径会被输出增长反噬

**免跑基线**（2026-08-19 u4-sub3-cost，designs/u4-sub3-cost-optimization-design.md §1）：上游节点的 A/B 实例若顺带跑过目标步且目标步代码零变更，其 drive-stream 里目标步的段就是**同种子同码现成基线**——按 result 事件切 segment（每段一个 result），段内第一个 assistant 事件的 usage=首调 fresh/cr，逐段 modelUsage=段合计。u4_sub2_ab B 轮 seg#4 直接给 u:4#3 基线（首调 44,747 cr=0 链恒冷/18 轮/13 探索 Bash），省掉一整轮基线重跑（~$1+5min）。前提三查：①目标步代码两轮间零变更（git log 核）；②种子 evidence 内前序 trace 与该轮跑出的是同一条；③段口径对齐（链内段 vs fresh 段形态写进混淆声明）。**墙钟=输出量主导**（同轮实测）：断链+strip+复用三杠杆后 token 轴全达标（首调 -66%/fresh -58%/cr -54%/成本等效 -56%）但段 dur_api +28.6%——分解发现同端点生成速率四样本稳定 121-129 tok/s，墙钟差 ≈ 输出差 ÷ 速率：复用钉死的逐字引用形态抬输出 +28.5%（引用更长=质量形态），生成主导下输出量即墙钟。**验收口径**：token/成本轴与墙钟轴分开归因——dur_api 先拆「out÷rate 拟合」，拟合得上则墙钟变化=输出量变化，别误判为优化失效或端点变慢；输出增长要再分「质量形态（逐字引用/更厚证据）vs 返工褶皱（Edit 重试/待填 grep 格式迭代）」两成分，前者是条款的兑现不撤，后者才是可消灭项。判别问句：段墙钟反向大涨时先算 out/rate——拟合上是输出量问题（查输出两成分），拟合不上才是端点方差或机制问题。**B2 复测确认（同日第二轮）**：首调 15,349 与 B1 15,309 双样本 ±0.3%（机制读数确定性钉死），墙钟 93s ≤ 基线 96s——B1 的 +28.6% 确为 scaffold 褶皱+输出离群的单轮方差。**断链暴露效应（#30 配套，双样本结构性）**：断链会暴露后续步被链上下文掩盖的条款缺口——u:4#4 链内 11 轮/60s/out 7.6k（格式上下文由前步会话携带），断链后 fresh 段两轮 10-24 轮/187-253s/out 25-34k：格式猎捕（#26，grep designs 反推载荷格式 5+ 调用——该步无「格式真源钉死」条款）+ evidence 元探查（#16，包尾邀请——pack_self_contained 未置位）。**断链前置核对扩面**：交接包材料完备性（#20）之外，补「链内后续步的格式钉死/材料边界条款缺口审计」——缺口先补再断，或断链与补款同批落地；否则首调 token 收益（双样本稳定 -59%）被步体爆炸吃掉总账。种子复原六件套补字段组：state 被推进过后复原须 phase/index/sub_index/node 四字段同步（只改 node 撞 normalize_state 一致性校验 rc=1）。

## 31. 骨架表达力缺口会诱发「仓内样例猎捕」——格式信息要随骨架形态完备；worktree A/B 验收面第三路径=模型 Bash 调引擎 CLI 走主树

**骨架多条形态提示**（2026-08-19 u4-sub4-cost，designs/u4-sub4-cost-optimization-design.md §5 修A）：#26 格式真源钉死条款灭了跨仓源码反推（B 双轮 designs/引擎源码翻找清零），但模型为确认「多条 statement 怎么写」仍花 5 调用查 evidence 实际样例（自白「这是格式核对，非 evidence 翻找」）——单条骨架未示多条形态 = **骨架表达力缺口**：条款管得住「不去反推校验实现」，管不住「骨架本身没回答的问题」。修法 = 多条形态写进 scaffold 待填占位符括注（「多条陈述 = 逐项重复本【statements】整段，一条一块」）——占位符替换即消失（与既有「（outcome 层，禁实现侧名词…）」括注同形态），零解析器变更，parse-back 测试钉死。判别问句：模型按条款不去翻源码、却去翻仓内实例找格式样例时 = 骨架没回答它的问题，杠杆在骨架表达力不在再加文案禁令。**验收面第三路径（#28 补）**：worktree A/B 生效面三分——①driver 侧（段 prompt 条款/spawn env·tools 覆盖/driver 装配的交接包，worktree 可控）；②SessionStart hook 侧（TUI 段交接包，主树引擎，#28 已登记）；③**模型 Bash 侧**（`append-trace --scaffold/--from-file` 等引擎 CLI——命令模板硬编码 `~/.dl-workflow/dl_flow_engine.py` = 主树，worktree 码的 scaffold/解析器/机械校验改动在 A/B 里**静默无效**，B2 骨架 Read 回显旧版实证）——③归 merge 后生效面写进设计遗留，别计入本轮验收也别误判「改了没效果」。**配套读数口径（#30 联用）**：消费装配步的 out 残量大头是载荷厚度（逐字引用六字段=质量形态），预登记 out/墙钟目标时别把「褶皱全灭」当前提——先拆褶皱 vs 质量两成分占比再定线（本轮 out 预登记 ≥50% 实测 -26% 的教训：褶皱成分比预估小，B2 唯一拒收是 mech 牙齿逮真漏[C7.2 传导缺失]=合法修正循环非浪费）。

## 32. 复用钉死的三条材料前提——截断边界全文入包 / 命令路径白名单兼容形态 / 种子产物文件；输出构成三分归因法

**复用钉死的材料前提三件套**（2026-08-19 p1-sub1-cost，designs/p1-sub1-cost-optimization-design.md §5）：复用钉死条款（#25/#29）要求「前序出处逐字引用零重验」，B1 轮实证条款单独落地会撞三面材料墙——①**P1-1 截断杀逐字引用**：交接包前序 statements.boundary 截断 100 字符（_PACK_PRIOR_BOUNDARY_MAX），截断处恰是 file:line/机制结论（双×100 链出处被切成「f…」），模型拿不到逐字出处只能翻 evidence grep×6+前序重验 ~10 调用；修法=Step.pack_full_prior_boundary 声明式置位（置位步包内前序 boundary 保全文，B2/B3 evidence 翻找清零）。②**命令路径的白名单兼容形态**：per-wf 白名单规则按**字面 ~** 前缀匹配（`Bash(bash ~/.dl-workflow/...:*)`），node-rules 发 _DLWF_ROOT 展开绝对路径（worktree 形）不在任何白名单形态内，acceptEdits 下 3 连「requires approval」——模型的「工具元探查/settings 翻查」实为**权限墙后的自救**，不是好奇；修法=命令路径按 driver 树分派（生产发字面 ~ 与 148d1e3 同形态，worktree 发绝对路径+种子侧 settings 补白名单），#31 验收面第三路径的权限变体：worktree 路径不仅主树无新码，也不在 per-wf 白名单形态内，A/B 前必核命令路径的白名单兼容形态。③**种子第七件=产物文件**：种子复原（#30 六件套）漏 .claude/understands/<name>.md 时包内无产物指针，模型 find/ls 翻 understand.md×4——种子完备性=「交接包产物清单节非空」冒烟可验。判别问句：条款落地后模型仍在翻找/重验时，先查「逐字引用的材料在包内是否全文可见」与「给它的命令是否真跑得通（白名单形态）」，别先加文案禁令。**输出构成三分归因法**（同轮）：段 out 增长时拆 thinking/text/tool_use 输入三成分——tool_use 输入降（调用数杠杆的直接兑现）而 thinking 涨（条款驱动的逐事实 deliberation，1.9×）时，墙钟（out÷rate）会被 thinking 反噬：调用数 -62% 而墙钟 +16% 的拟合实证；验收口径=token/成本轴（等效 -51.4%）与墙钟轴分开登记，thinking 密度=输出侧瘦身观察项。**段 fresh 合计降幅的工具输出稀释**：首调 fresh（前缀机制读数，-55.8% 双样本逐字相同钉死）与段 fresh 合计（-17.7%）要分开预登记——合计大头是工具输出增量逐轮进上下文，调用数杠杆被大体积输出稀释，别用合计口径判前缀杠杆失效。
