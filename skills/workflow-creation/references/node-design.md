## 3.8 编排节点拆步方法论（设计新 sub_steps 前必读）

八个编排节点（ProblemContext 7 步 / GoalsAndValue 5 步 / ScopeAndConstraints 5 步 / SuccessCriteria 5 步 / DesignSolution 6 步 / TaskBreakdown 5 步 / CapabilityToolSelection 6 步 / ExecutionPlanCheckpoints 5 步）沉淀的第一性原理推导链。设计文档是全貌（各 `designs/*-substeps-design.md`），本节是浓缩的推导顺序：

0. **领域定位先于失效模式分析**（2026-07-28 DesignSolution 初版被驳回 + understand:3 编程域修订，同一用户决议「编程专用工作流」两次兑现）：失效模式表是**领域相关**的——编程工作流的解必须锚定代码现实（「凭空设计」是不看代码就设计/引用不存在接口/重复造轮子，编程域主导失效族，通用域没有），消费契约倒推的产物形态也不同（理论方案 vs 代码级改动清单）。DesignSolution 初版套通用域失效模式表产出 5 步理论方案版，被用户「编程工作流不能只理论，要结合项目代码做代码设计方案」驳回——重做失效模式分析才多出接地族（5→6 步）。设计新节点前先问：**这个节点的命题在本领域（编程）里长什么形态**？
1. **终态三属性定目标**：内容正确（中间步）/ 形式可移植（归一化陈述步）/ 用户认可（读回确认步）——三属性同构贯穿所有 understand 子阶段，末两步（归一化 + 带证据读回）是固定收尾对。
2. **命题性质三分定取证配置**（2026-07-27 从二分扩成三分）：
   - **事实性命题**（问题是否存在、约束是否真实）→ 需取证 + 质检裁决（judge 判结构、外部证据判真值）；
   - **规范性命题**（想要什么、范围取舍、must/nice）→ **无取证步**——外部证据无权证伪「我想要什么」，真值源只有用户（硬设取证步 = 逼模型拿「业界通常」式训练记忆冒充依据）；
   - **中间态（假设）**（未证明但当作真）→ 显式标注（置信度 × 错误时影响）+ **接受归用户**（风险承担是规范裁决，模型无权代答）。
3. **取证源深度定取证步数量**：五层外部源（OpenAlex/arXiv/SE/HN/GitHub）→ 取证过程与判断质量异族，拆双步（ProblemContext 子4+子5）；本地单层源（Bash/codegraph/Read 验证项目内部事实）→ 压缩为一步（ScopeAndConstraints 子2），独立质检步判无可判 = 纯烧 judge。 **档随原子走，不随步走**（2026-08-02 v2.40，designs/fetch-depth-tiering-design.md）：同一取证步内原子问题的深度可以异质（仓内可答/点查锚点/充分双向）——按步定档会把混合实例逼进最深档纯烧。模式三件套：**分类前置**（上游步定档+其 gate 判分类合理性——纠偏在便宜环节）、**执行步只执行不重判**（禁降档——弱模型不给二次裁量口）、**升档通道**（执行中发现不收敛可上报升级+留痕——质量兜底）。**默认档按失败模式不对称选居间**：漏取证=质量问题（难发现）、过度取证=成本问题（易发现）→ 拿不准归中间档。
4. **失效模式族定步数**：先列失效模式表（每条带外部出处），再按族归并——异族拆开（judge 分步可判），同族合并（省 judge）。步数不是模板对称出来的（6≠5≠5≠5），是失效模式族数出来的。**设计期外部取证惯例**（2026-07-28 plan:2/plan:3 两例）：失效模式表的外部出处用 Tavily 检索（用户明示允许时），设计文档头部注明「设计期调研——与运行期 understand:1 子3『禁 tavily/WebSearch』约束无关」免误读；编程域失效模式优先找 LLM 工具使用/agent 失效的实证研究（tool hallucination 分类、tool overload 基准等），通用项目管理文献对编程域判据无效。
5. **每个新节点先写「关键不对称」**：与前序节点的差异即设计轴心（ProblemContext=纯事实、GoalsAndValue=纯规范、ScopeAndConstraints=混合[约束事实+范围规范]、SuccessCriteria=混合[轴心=规范性目标的可检验化转换；**消费契约倒推**——产物字段从下游消费方（review:0 rubric 判定需求）倒推，不是拍的]、DesignSolution=混合[**创造性生成×代码接地双轴心**——首个创造性生成节点：对象不存在须发散（防 design fixation），解必须锚定本仓代码现实须勘察（防凭空 API/重复造轮子）；消费契约倒推同 SuccessCriteria，下游=plan:2/execute:0/review:0]、TaskBreakdown=混合[**保真转换×执行接地**——与 DesignSolution 镜像：输入对象已存在且已拍板，创造性已上游消费（**无发散步**，发散=逼编造伪候选），主敌换成转换失真（semantic drift，防=清点基线+追溯锚）与执行者视角虚构（零上下文 executor 消费编造锚点，防=锚点核验步）；消费契约倒推，下游=execute:0/executing-plans/review:0]、CapabilityToolSelection=混合[**有限枚举×配置接地**——能力空间=可枚举注册表非生成空间（无发散步），主敌是映射层失效：幽灵能力（ghost invocation，f̂∉F，防=注册表逐字出处）/能力错配（防=trigger 原文覆盖判据）/tool overload（防=最小集+显式不加载清单）/漏配强制项（防=强制路由逐任务核对）；消费契约倒推，下游=execute:0/using-superpowers/H15+执行映射/Agent 成本/overload 防线五方]、ExecutionPlanCheckpoints=混合[**时序控制×风险配平**——首个运行时控制结构设计节点（前七节点设计内容，本节点设计控制流：何时停/验什么/失败后去哪/谁可并行）+首个四源聚合节点；主敌是时序失效：检查点虚设（防=零判断词判据）/误差复利（防=阶段边界布点+goal anchoring）/密度失配（防=密度归用户裁决+可逆性×爆炸半径提案）/失败处置缺失（防=路由三选一预定义）/并行冲突（防=互斥面交集实算）/返回物无验收（防=返回契约）；消费契约倒推，下游=execute:0 orchestrator 愿景（executor 不自行分析+多 subagent 并行）/execute:0 rubric/understand:4 时机字段/review:0 证据/用户密度裁决五方]）——照抄前节点步数/结构而不重做失效模式分析 = 设计事故温床（各 design 文档「否决的替代方案」节都否过一个「全对称版」）。

测试」这种抽象预见不够——**设计期逐函数走查一遍**（读代码，不是读设计；机制断言——含讨论稿的「必须保留 X」式主张——先查最近同构先例的节点定义再下结论，2026-07-28 实例：讨论稿凭记忆主张 plan:2 gate_rubric 不能置 None，查 understand:4 先例[阶段出口编排节点 rubric=None + 7. **设计文档的修订留痕格式**（2026-07-28 understand:3/4 编程域修订惯例）：已确认的设计文档做定位级修订时——头部加一行 `> 修订（日期，用户决议）：定位 + 改动点清单`，正文修改处嵌「（日期 修订）」标记——让后续读者分清原始设计与后补修订，且修订决议本身可溯源。
8. **数据面卸载是拆步的正交轴**（2026-08-01 v2.38 子3 子代理化）：#3 按取证源深度定步数，但**步内工具密度**是另一轴——外部取证类步骤的原始输出（curl/WebFetch 页面）是主会话上下文长度大头（成本=轮次×长度，§3.6 #8）。判据：步骤的产出是**蒸馏结论**而原料体积大 → 原料采集卸子代理（`*-prompt` 生成器 + 返回契约=蒸馏边界，§3.7 四件套），主会话只做 可检验化/派发/原文收录/内部层；产出是**判断/裁决**或原料本身小（codegraph/Read 仓内）→ 留主会话。编排结构（步数/gate/留痕要求）不变，只换执行位置——配套三件事：fence_allow 加 Agent（子代理进程工具经同一 PreToolUse 围栏，不区分主/子会话）、原文收录形式要件机械化（§3.5 #17）、红线规则随迁（§3.5 #18）。

9. **会话粒度是拆步的第三正交轴**（2026-08-13 P2-4 段链合并，designs/segment-chain-resume-design.md）：#1-5 定门控粒度（步），#8 定数据面执行位置，**会话粒度**（一个会话覆盖几个步）是第三轴——三者独立可调。核心鉴别：**会话合并 ≠ 派发合并**——v3.0 §2.2 否「批量段」的两个理由（append-trace state 驱动错挂步号 / 弱模型多步指令跟随=一过率对立面）都只针对「一次派发多步」；「逐步派发 + `--resume` 同会话续跑」两个都不触及（步号归属由逐步派发保住，单步指令由每 prompt 只带当前步 purpose 保住）。**链边界三论证同指 minor_state**：①node-rules system prompt 按节点生成——跨节点续跑 system prompt 变 = 前缀缓存失效；②handoff_pack 交接（v2.45）在 minor_state 边界重置上下文——链不超边界则 v2 平方膨胀不复发（v2 教训边界 = 30+ 步无锯齿；链内 3-5 步峰值 ~150-250k 有界）；③交互步（TUI 段）/确认步（无会话）天然断链。续链不变式（链属当前节点 + last_step == cur-1）让 state-reset/back/jump/step-pass/TUI 全部**天然失配断链**，需显式断的只有 RC_INTERRUPTED（杀中段 transcript 尾或残半 turn）。**收益按 provider 缓存语义分流**：流式会话隔离 provider（deepseek 类）上 = 摊薄冷启动的唯一杠杆；流式全局共享 provider（kimi 类）上收益≈0——同一优化不同 provider 收益差一个量级，设计目标值必须按缓存探针矩阵（v4-cost 设计 §2.0b）分流写两套。
10. **取证源选择 = 先识别权威类型、定点抓，泛搜索兜底**（2026-08-13 amplitude_annualized sub3 审计）：「年化折算」是工程惯例不是学术问题——权威在业界标准库源码（empyrical/pyfolio），不在 OpenAlex/arXiv 关键词索引。light+full 两 agent 17 curl 仅 4 次有效（24%），其余泛搜索全空手/无关/权限受限；有效那 4 次全是「定点抓 empyrical 源码」。设计取证步（尤其方法论/量级合理性 claim）时三件事：①**先判权威类型**（学术论文 / 业界库源码 / 官方文档 / 定点网页——给模型一张 domain→权威源注册表，不靠它临场判断）；②**查询词翻译成业界术语**（禁 repo 内部黑话，如 coverage → annualization with missing trading days）；③**泛搜索（OpenAlex/arXiv/SE/HN）只作注册表无对应项时的兜底**。判据：claim 的权威是「单一已知源」还是「需泛搜索发现」——前者定点抓（高有效率），后者才泛搜。

11. **拆步重编号先查 sub_step_index 类型——int 就全重编号，别想后缀**（2026-08-14 plan-first 拆步，understand:1 子2→子2a/子2b）：想给拆出的两步用 `2a/2b` 后缀标识，但 `sub_step_index` 全链路是 **int**（`sub_step_at(node, n: int)`、`range(1, sub_step_index+1)`、evidence 匹配 `sub_step == n`、`_iter_trace_segments(text, n)`、state 范围校验），加后缀要 int→str 改语义，波及 range/比较/evidence 匹配/state 一大片。int 约束下只能**全重编号顺延**（子2→2/3，子3-6→4-7），机制简单但波及面大——evidence 历史 sub_step 值全变 + 读回步挂载/segment chain 白名单/注入文案里的步号 + **跨节点"同构 ProblemContext 子N"引用**（别的节点 purpose 里指向本节点的步号）全要顺延核对。设计"拆一步成两步"前先 grep `sub_step_index` 消费面 + 跨节点步号引用，确认类型约束再定编号方案。
12. **提效优化先定位瓶颈层——搜索次数 / 判断思考 / 上下文膨胀是三个不同的层，在"搜索"层加工具碰不到"判断"层**（2026-08-14 amplitude_annualized step2 实测）：一整条线优化"搜索"（codebase toolbox 合一查询 / discovery ledger 去重 / `dl codebase trace` 全景 / 取证路线模板 / 围栏禁 grep），实测墙钟 6min 不降——因为瓶颈是**两次搜索之间的判断思考**（读工具结果 + 形成因果假设 + 决定下一步，最长 79s 间隔），不是搜索本身（单次 grep 0.3s）。最后 plan-first 拆步（把"规划思考"从"执行搜索"里分离成两步，即 #3 分类前置的兑现）才从 6min 降到 ~3min。教训：动手提效前先按 drive-stream 的 tool 间隔分诊——若大头是 **tool 间 gap（思考）** 而非 tool 数/单次耗时，那搜索工具优化（合一/去重/全景）全在错的层；判断思考层的杠杆是**拆步分离**（#3）或**上下文瘦身**，不是加搜索工具。实证判据：**tool 调用数降了但墙钟不降 = 瓶颈不在搜索层**（换个层，别在同一层继续堆）。
13. **框架通用 vs 项目专属边界——进框架的工具/模板只做代码结构语义，领域模板走 component B 注册**（2026-08-14 codebase-toolbox 全程）：dl-workflow 会跑任意代码项目，任何进框架的工具/模板/方法论必须**跨项目通用**（codegraph/git/grep 的代码结构语义：symbol 定义/调用/影响面/历史），不能耦合任何项目的数据契约（回测 schema、report 数据流）。领域模板（如 factor 年化怎么拆）走 **component B 工具注册**（`<项目>/.claude/workflow-tools.yaml`）+ 项目级 skill，各自维护、不污染框架。设计进框架的东西先问一句「这是框架通用还是项目专属」——项目专属的硬编码进框架 = 换项目就废（"数据流"这种词就是项目语义，通用等价物是 codegraph 的 callees）。
14. **工具可用 ≠ 模型自动会用——新通道的「进入条件」要在该步 purpose/selfcheck 里显式声明**（2026-08-14 amplitude_annualized step3 修复后实测）：`dl codebase` 文案从 broken 的 `dl codebase` 改为可跑的 `bash dl-cmd.sh codebase ...` 后，模型确实用了，但探索面扩大 39%（+23 轮）。根因不是工具错，而是该步 purpose 只写了「取证路线」，没写「同类查询优先走 codebase、禁止为凑证据扩大探索面」的**停止条件**。给某个子步骤配新工具/新通道时，三件事一起改：①工具/文案（让命令可跑）；②purpose（明确何时用它）；③selfcheck（明确什么时候该停）。缺 ③ = 模型有枪没刹车。
15. **通路与台账要同时验收——`discoveries.jsonl` 生成是 `dl codebase` 被真实使用的硬指标**（2026-08-14 实测）：修复前模型用 raw grep/裸 codegraph，工作流目录无 discoveries.jsonl；修复后 `bash dl-cmd.sh codebase ...` 可跑，ledger 首次生成 18KB。检查台账是否生成，比检查「模型有没有被 deny」更能证明工具通道真的生效。
16. **文案约束管不住弱模型的步骤越界——「只做 X」要用机制堵入口，不是靠 purpose 劝阻**（2026-08-17 amplitude_annualized 6 轮对照，v2.44 探索预算）：子2a purpose 明文「只规划不挖链」，弱模型 deepseek-v4-flash 仍跑 38 次 codebase/find 探索、56 轮、上下文胀到 114k（子2b --resume 继承后 fresh 124k）——它把执行冲动（定位实现符号）提前到了规划步。**文案约束对弱模型结构性失效**：它读得懂「只规划」但控制不住「想先查清楚再规划」。机制解 = `Step.max_explore_calls` 探索预算：drive_mode 段工人对 codebase/find/codegraph 探索命令机械计数，超限 PreToolUse 硬 deny（堵入口，deny 文案指路回本步交付物 atomic_questions）。iter5/6 连续验证：子2a 稳定 15-17 轮、6-7 次探索（预算内收敛，零 deny）、合计耗时 692s→365s（-47%）、成本 -50%。**判别准则：一个「只做 X 不做 Y」的步骤边界，若 Y 是弱模型的自然冲动（先查清楚再动手），文案约束必失效，唯一可靠的是 PreToolUse 计数/白名单类机械拦截。** 与 #12（瓶颈分层）互补：#12 定位「思考层」后，本条给「思考层失控」的机制解。
17. **零和游戏检测——把活从步骤 B 搬到步骤 A 不叫优化，叫转移**（2026-08-17 u1-sub2b-consumes-sub2a 实测翻车）：让子2a 手写 `symbols`/`files` 字段「为子2b 锁定取证入口」，实测子2a 16→119 轮爆炸（$1.52→$14.55），子2b 只 35→19 轮——**净亏 2.3×**。教训：优化前先问「这个动作总工时变了吗，还是只是换了步骤受罪」。真正的优化是**消灭**动作（子2b 不再重新探索），不是**转移**动作（把探索推给子2a 手写）。检测信号：上游步骤轮数暴涨而下游只省一点 = 零和；下游省的 > 上游涨的 = 真优化。配套：**让模型手写它需要「凭空想」的产物（符号清单）= 把最难推理活塞给最弱环节**；机械能从已有行为导出的（工具落账），就别让模型手写。
18. **grep 命中面 ≠ 取证起点——字符串搜索的命中文件清单是噪音不是信号**（2026-08-17 string-files 注入翻车）：把 `dl codebase query --string "annual"` 命中的文件自动落账并注入子2b 当「取证起点」，结果 350 个文件（test_cases/docs/MODULE.md 全命中）灌进 node-rules，注入块 18.8K chars 反而膨胀上下文。**字符串搜索是「面」（命中一切含该词的文件），结构查询（trace/callers/history）才是「点」（file:line 精确锚点）**。取证起点只能来自结构查询，不能来自 grep 命中面。判别：注入给模型的「起点清单」若含 test_cases/docs/规范文档 = 噪音混入，真正的代码锚点不会被这些词命中到前几名。
19. **step2→3 这类「--resume 续链」的上下文膨胀，根因是前一步轮数失控，不是注入大小**（2026-08-17 fresh 124k 误诊纠正）：实测 step3 首调 fresh 124k，先以为「deepseek 流式会话隔离缓存」或「注入膨胀」，实际查 drive-stream token 流向——step2 跑 52 轮会话内上下文累积到 114k，step3 `--resume` **继承**这个 114k。**同会话续链时，fresh 大头 = 前一步的 transcript 长度**，注入（node-rules 9.7k + 交接包 9k + PROJECT.md 23k）只占小头。诊断 fresh 膨胀先分两种情形：①跨段新会话（真 cold start，provider 缓存语义相关）②同会话 --resume（继承前一步 transcript，前一步轮数是主因）。情形②的杠杆 = 压住前一步轮数（#16 探索预算），不是注入瘦身。
