### 1.4 多会话并发维护（单人 ≠ 单会话，2026-07-28 实测）

系统文档写「单人维护直接在 main 开发」，但**单人 ≠ 单会话**：两个 Claude 会话可在同一 `~/.dl-workflow` 并行作业。当日实测：一方 `git reset --hard`/restore 把另一方**未提交**的改动抹掉（两文件全失），残留文件与新状态不一致（tests 期待新节点而节点树被回退，46 failed）。

- **防御**：未提交工作 = 丢失面 + hunk 混合冲突源。**完成一个逻辑单元就 commit**（frequent small commits 对共享 repo 是防撞保护，不只是整洁）；知道另一会话在同 repo 作业时更要即改即提——攒到「划分 commit」才提就是给冲突留窗口。
- **诊断**（发现改动消失，别急着重做）：`git status`（文件还在不在 M 列表）→ `git log`（**HEAD 前进 = 对方已提交你的工作，转验收；HEAD 不动 = 被回退**）→ `git reflog`（reset 事件留痕）→ grep 文件内容确认。关键分叉：被提交（好消息）vs 被回退（需裁决）。
- **恢复纪律**：先 surface 给用户——回退可能是对方有意，盲目重做会制造第二轮冲突；若对方已提交，**全量验收代替重做**（pytest 全绿 + ruff + grep 关键标识 + install copy diff + render/注入冒烟）。

## 3.9 多会话同仓协作（并发编辑信号 / commit 拆分 / 时序验证）

（被回退侧的恢复协议——诊断分叉「被提交 vs 被回退」+ 全量验收代替重做——见 §1.4；本节是并发进行中的写者侧视角。）

2026-07-28 实例：本会话做 understand:3/4 编程域修订时，另一会话同仓做 plan:1 编排——两批改动交织进同一文件（dl_flow_nodes.py / SKILL.md），完整走完「发现并发 → 分工 → 拆分提交」全流程，沉淀四步：

1. **另一写者的早期信号，任一出现先停手问用户**：Edit 工具提示「file modified on disk since you last read it」；两次 `git status` 之间文件列表/mtime 变化；目标文件 mtime 就是当前时刻。**绝不双写同一文件**——当日 test 文件差点两会话同时编辑。
2. **大批量测试失败的归因法**：先 `git stash` 跑基线——基线绿 = 失败全来自工作区改动而非你的编辑；再把 FAILED 清单归并到单一根因（重编号/拆分类 breaking 改动 = N 失败一根因，逐个修是误诊）。归因后才决定：自己的失败修，别人的失败留。
3. **同一文件交织两批改动时的 commit 拆分（重建法）**：本环境无交互式 `git add -p`，替代 5 步——①两批终态文件 cp 到 /tmp；②`git checkout HEAD -- <混合文件>`；③重放己方编辑（Edit 工具按已知 old/new 逐处，重放后 `diff` 对照终态，**只在对方区域有 hunk** 才算重放正确）；④跑「HEAD 版测试 + 己方改动」验证绿 → 提交己方——**己方改动含文案/输出文本变更时，先 `grep` 对方未提交的测试文件是否断言该文本**（2026-07-28 state-reset 实例：门栏提示文案改词，grep 确认 test_workflow_advance/phase 零断言才敢提中间态；有断言则中间态必红，需先协调分工而非强提）；⑤cp 回终态 → 全量验证 → 提交对方。
4. **提交时序的验证错觉**：先提交的 engine 改动配「来自未来的已迁移测试」跑会红一片——这不是回归，是测试与代码的时序错位；正确验证 = `git checkout HEAD -- tests/` 跑绿再恢复（③的验证步）。**别把时序错位当 bug 修**。
5. **`git add -A` 是并发下的席卷动作**（2026-07-30 实例）：会话 A 的 `_INTERACTIVE_CHUNKING_RULE` 改动未暂存过夜，会话 B 提交自己批次时 `git add -A` 把它席卷进 B 的 commit（377e898，message 未提）——没丢（对方后补文档 commit），但归属和 message 都失真。规则：**dl-workflow 仓改完立即 commit，不留未暂存改动过夜**；提交前 `git status --short` 逐文件确认全是自己这批（本环境无 `git add -p`，发现夹带按 #3 重建法拆）；并发活跃期优先 `git add <明确文件清单>` 不用 `-A`。
6. **编排版本号 commit 前先查占用**（2026-07-31 实例）：v2.xx 序号无中央分配——本会话按 memory 记的 v2.31 往下排，实际另一会话的产物机械门（7097c48）已先占 v2.31，被迫补一个改名 commit（ba3485b）。提交前 `grep -rn "v2\.<n>"` 全仓 + `git log --oneline -5` 查最新序号。 **并行泛化期还要查工作区未提交的并行 design 文档自称的版本号**（2026-08-04 u:2#4 实例：并行 u:2#3 的未跟踪 design 文档自称 v2.86 与**已入库** v2.86 撞号——git log 查不到未提交占用，grep 全仓（含 untracked）才能看见；取号=已入库与工作区自称的 max+1）。
7. **format/lint 漂移归因：先确认归属，独立批收口**（2026-08-02 v2.41 实例）：`ruff format --check` 报 5 文件漂移但都不在本次改动行——根因 = **committed 代码 + ruff 版本口径变化**（旧版本格式化的行被新版规则重排），不是并发污染也不是你的编辑。处理纪律：①先 `ruff format --diff <文件>` 看 hunk 归属——落在自己改动行 = 自己新代码没过 format，随本批修；全是别人/历史行 = pre-existing 漂移；②pre-existing 漂移**不混入功能 commit**（守 #3 批次纯净），独立 style commit 收口 + message 声明非语义改动；③format 跑完**必复跑 pytest 再 commit**（症状 M checklist #7 同纪律）——且 format 可能顺带带出你刚写的新行（本次 test_workflow_phase.py 一行，属①随批修）。

8. **仓级 `ruff format .` 在并发期是席卷动作（与 `git add -A` 同族）**（2026-08-04 v2.85 实例）：跑一次 `ruff format .` 重排了 9 个文件，其中 7 个是另一会话刚建的重放资产（`replay_u1_sub1/2/3.py`、`_common.py`、`test_codegraph_gate.py` 等）——纯格式无实质改动、713 tests 全绿，但**它们不是你的批次**。处置纪律：①并发活跃期把 lint 范围收窄到自己的文件（`ruff format <明确清单>` 而非 `.`）；②已经席卷了就**只 `git add` 自己的文件**，别人的格式改动留在工作树（对方下轮跑 ruff 自然吸收，或由其自行决定）——混进自己 commit = #5 `git add -A` 同款归属失真；③例外：若该格式改动是你修的**通道/共享件本身**（本次 `_common.py` 的 token 优先级 bug），则连带格式一起提，因为职责在你这轮。判据 = 「这文件的**语义**改动是不是我做的」，不是「谁先建的」。
9. **节点产物部分提交：共享文件归属他人时，先提零冲突的新文件、共享文件改动留待归属会话收口**（2026-08-04 u:2#2 实例，be1f8db）——并行会话 A 做 u:2#2（design+replay+gate 代码+测试），但 gate 代码/测试/skill/README 与在飞 u:2#1 改动同文件。A 先只提交 design+replay 两个**新文件**（零冲突），commit message 明示「gate 代码改动（dl_flow_nodes.py 子2）+ test pin + skill + README 行在与并行 u:2#1 改动同文件，待并行会话一并提交」——共享文件改动留待归属会话收口。判别：`git status --short` 区分「纯自己新文件」（design/replay，永远可先提）vs「混他人未提交改动的文件」（先不碰）；`git add <明确清单>` 只收自己的。与 #3 重建法的分工：先发防撞用本条「先提新文件」；事后拆夹带用 #3「重建法」。
10. **权限分类器「Interfere With Workloads」在并发期误触发：先验真状态再拿授权，禁换写法绕过**（2026-08-04 u:2#3 实例）——编辑近期被并行会话提交/改过的文件（如 dl_flow_nodes.py）时，auto 分类器可能以「干扰并行会话在飞未提交状态」deny 合法编辑，尤其当会话内用户指令含「提交他人改动」这类模糊表述（分类器把合法编辑误关联到 commit 他人未提交工作）。解围三步：①验真实际状态——`git status --short` + `git log`：并行会话已提交则文件干净、无他人未提交改动，分类器前提不成立；②把状态 surface 给用户（「无他人未提交改动、编辑纯属本人工作、提交用显式清单」）拿明确授权；③授权后重试即过。**禁盲目换写法/工具试探绕过**（同 #31 凭证类分类器纪律）——正确动作是状态验证+用户授权，不是绕。
11. **共享「清单文件」的席卷比代码文件更隐蔽——按 HEAD 重建暂存区，别用 `git checkout` 回退**（2026-08-04 u:3#1 v2.91 实例）：`tests/replays/README.md` 这类**追加式清单**（每个节点加一行）是并发泛化期的必然共享点，且**双方的改动天然无语法冲突**——所以 Edit/Write 不报警、`git add <显式清单>` 也拦不住（文件确实在我的清单里，只是文件**内容**混了对方的行）。本次 `git diff --cached` 复核才发现暂存了对方的 `replay_u3_sub3.py` 行。处置**不能**用 `git checkout HEAD -- <file>`（会连自己的行一起丢，还抹掉对方工作树改动）；正解三步：①`git show HEAD:<file>` 取基线；②基线 + **只加自己那一行** → 写盘 → `git add`；③再把对方的行追加回工作树（保持对方改动在场，由其自行提交）。判别纪律：**`git add` 后必 `git diff --cached <共享文件>` 逐行确认**——代码文件的席卷会被测试/语法逮住，清单文件的席卷只有肉眼复核能逮住（与 #5 `git add -A` 同族，但触发条件更宽：显式清单也不免疫）。
12. **共享 pin 函数是「同文件同函数不同行」的最小冲突单元，先落地者胜、后落地者补自己那行**（2026-08-04 u:3#1 实例）：`test_default_pass_marker_pinned_in_gates` 按节点坐标逐行 assert（u:1 五行 / u:2 四行 / u:3#1 一行……），并行会话反转不同节点时**必然同时改这一个函数**。本次两会话各加自己节点的 assert 行，无冲突落地——因为**每行只断言自己节点、行间零耦合**。这是可复制的设计属性：**并发期共享的测试 pin 应写成「逐坐标独立 assert」而非「循环遍历坐标族」**——坐标族（如 `_FIVE_STEPS` 列表）改的是同一个字面量列表，两会话同时加 = 真冲突；逐行 assert 改的是不同行 = git 自动合并。回顾 §3.5 #30 ㉔「pin 审计须 grep 坐标族」——坐标族在**并发期**还额外是冲突源，反转节点时优先加独立 assert 行，别把新节点塞进既有坐标族列表。
13. **版本号 mid-session 被并行提交抢占——设计文档里的版本号是易失声明**（2026-08-04 u:3#4 v2.92 实例）：起手取号按 #6（已入库+工作区自称 max+1）得 v2.91，但并行 u:3#1 会话在**会话中途**以 v2.91 提交，我的 design 撞车。判别：`git log --oneline` 在**提交前**再看一次（不是取号时看一次）。处置=重编号（design 头 + replay docstring + test comment 三处文本替换，成本低），不必改代码逻辑。**与 #6 的分工**：#6 防「取号时撞工作区自称」；本条防「会话进行中撞新提交」——并行泛化期两者都要查。 **操作化补丁**（2026-08-04 u:3#2 v2.94 实例）：「提交前再看一次」不只看 `git log`（已入库占用），还要**重跑 #6 的全仓 `grep`（含 untracked 自称文件）**——取号后到提交前的窗口期里，并行可能新建自称该版本号的未跟踪文件（本次取号 grep 时并行 `replay_u4_sub1.py` 尚未创建，提交后才出现、docstring 自称 v2.93 撞车，amend 改 v2.94 解），`git log` 看不到未入库占用，只有 grep 能逮。**replay docstring 也自认版本号，不只 design 文档头**（#6 原语境 grep design 自称，replay 脚本 docstring 同样自称，盲区同此——grep 全仓即覆盖，但取号时若只盯 design 会漏）。amend 改号同理须重 grep。
14. **共享 pin 逐行 assert 也 tangle + 分类器误拦「只 add 新文件」**（2026-08-04 u:3#4 v2.92 实例）：(a) 即使按 #12 逐坐标独立 assert，两会话在同一 `s3 = nodes._NODES[...]` assert 块各加行（u:3#2/#3/#4 三个节点同时落地），且一方补了重复的 `s3 = nodes...` 赋值行——**提交前检查共享 pin 函数内是否有重复赋值行**（重复行无害但留污染，收口会话清理前先 surface）；(b) auto 分类器把「显式 `git add` 两个新文件（design+replay）」误读为「提交共享编辑绕过协作协议」deny——#10 的「验真+surface+授权」通道解决，但实例说明**并发期连合法最小提交（只 add 自己的新文件）都可能被拦**：验真 git status 证明「无他人未提交改动被波及」+ 把「只 add 新文件」意图 surface 给用户拿授权即可，不必换写法绕过（#10 纪律）。
15. **编号抢占不止版本号：例数与条目编号同样是易失声明，且沉淀条目还会插错位置**（2026-08-04 u:3#3 v2.90 实例）——#6 防取号撞工作区自称、#13 防版本号中途撞新提交，但并行泛化期被抢占的编号维度还有两个：①**例数**（「泛化第九例」自称——三个并行会话中途提交了第九/十/十一例，真序=第十二）；②**条目编号**（㉗㉘㉙ 撞 v2.91 已入库的 ㉘㉙㉚ 与 v2.92 的 ㉜㉞）。更隐蔽的是**插入位置**：按文本 anchor（v2.88 的 ㉖ 段尾）插入沉淀条目，落点会在后来提交的三条例**之前**=时序错序。纪律：写 skill 沉淀条目前 `grep -o "泛化第.*例" 真源 | tail` + `grep -o "㉟\|㊱\|…" 真源` 查最新已占用编号（**提交前再查一次**，#13 同纪律）；插入位置取**条目族真尾**（最后一条例之后、下一大节之前），不取历史段落的 anchor。
16. **「在飞工作」证伪禁忌：快照没见到 ≠ 不存在**（2026-08-04 u:3#3 实例）——用户说「u:3#2 正在泛化」，会话初 `git status`/文件扫描无 u:3#2 痕迹，会话断言「在飞的是 u:2#3」并表面化纠正用户——**用户是对的**：u:3#2 会话的 design/replay 文件是会话进行中才创建的（并行会话起手先做基线重放、不立刻落文件）。#1 说「发现并发信号先停手问用户」；本条是镜像：**没发现信号不等于对方不在**——并发活跃期会话初快照几分钟即过期。用户坐标前提与快照证据冲突时的正确措辞=「我这边当前工作树未见痕迹，按你的坐标继续」（目标明确就照做），禁断言「不存在/记错了」。
17. **等并行收口期间用一次性定时检查而非轮询**（2026-08-04 u:4#2 v2.95 实例）——#9 是「先提零冲突新文件」，本条是其后的等待期纪律：用户裁决「等并行会话收口后再落地共享文件改动」后，**用一次性定时任务间隔化检查收口状态**（触发时 `git status --short` + `git log --oneline -2` 看目标共享文件是否从 M 变干净），而非 spin-poll——并行会话改文件是持续事件、无完成信号可轮询，轮询烧上下文；定时检查天然间隔化。判别「收口完成」的信号：目标共享文件（dl_flow_nodes.py / test_dl_flow_engine.py / README）M 消失 + mtime 停更数分钟 + `git log` HEAD 前进（对方已提交）。落地时仍走 #3/#9 纪律（显式清单 commit、禁 add -A、提交前 git log 复核编号）。本会话落地：ed408ad 先提 design+replay，20:03 定时检查。
18. **编号审计必须用字符类正则全量扫描，禁逐字枚举；且沉淀前先读 collab 最新条目**（2026-08-04 u:4#1 v2.93 实例，#15 的操作化补充——本会话**亲自踩了 #15 描述的坑两次**）：(a) 我按「已占用编号」查了 `㉒-㉟` 逐字枚举，落笔 ㉜㉝ 后才发现与 v2.92 已入库的 ㉜㉝ 撞号；重编号到 ㊱㊲ **又撞**（v2.92 后续条目已占到 ㊵）——**逐字枚举必然漏掉你没想到的号段**，正确姿势是 `python3 -c "import re;print(sorted(set(re.findall(r'[㉑-㉟㊱-㊿]', open(f).read()))))"` 全量扫描取 max+1，并在重编号后复核**无重复计数**（`collections.Counter`）——「改完不复核」是撞号第二次的直接原因。(b) 更根本的时序错误：我**先提交沉淀（04703d6）才读 collab #15/#16/#17**，而 #15 正是防此坑的规约——并行泛化期 collab.md 本身在被高频追加，**写 skill 沉淀条目前先读一遍 collab 尾部**（对方可能刚加了约束你的规约），与 #13「提交前重查版本号」同族但对象是**规约本身**而非编号。（**当日再实证**：u:4#3 会话写 collab 沉淀时以 `grep '^16\.|^17\.'` 定点查代替读尾部全文，漏看 u:4#1 已入库的 #18/#19，撞号 #18 被迫重编——grep 跳读不等于读尾部，操作姿势写死=Read 尾部全文）。
